摘要（中文翻译，忠实原文）

Agentic AI 为自动化复杂的建筑工程工作流提供了巨大潜力。然而，大多数现有应用仍是孤立的 PoC 演示，缺乏可复用领域能力、经人类验证的评估案例、以及标准化 benchmark 基础设施。本文提出 Buildrix，一个开放的、社区驱动的平台，用于开发、分享、执行和评测面向建筑工程的 agentic AI skill。Buildrix 集成三个组件：(1) Python 命令行包，用于开发、验证、发布、安装和管理 skill 与测试用例；(2) 基于 Web 的 Hub，用于组织开放挑战、可复用 skill、测试用例、评审与 benchmark 结果；(3) 本地 agent harness，支持 skill discovery、外部 toolchain provisioning、progressive context loading 和多步工作流执行。Buildrix 中的 skill 组织为标准化、自包含 的包，包含任务指令、可执行脚本、依赖以及支撑资源。定量测试用例可由领域专家验证并晋升为golden test case，用于可复现的 benchmark 评测。Buildrix 为可复用能力开发、透明评测和社区驱动的建筑工程 agentic AI 演进提供了开放基础。

核心内容解读（问题 / 三组件设计 / skill 包契约 / golden test 晋升机制 / 与 harness 工程谱系的关系）

问题背景。建筑工程行业里 agentic AI 应用有两个结构性痛点：(a) 演示分散不成生态 —— 每篇论文都造自己的 PoC，能力无法跨项目复用；(b) 评测靠自证 —— 没有社区级 golden test，任何"新方法比 baseline 强" 的 claim 都难以验证。作者主张：agentic AI 的下一步不是造更多单点 agent，而是给单点 agent 造"可分享的领域生态"。这个诊断和 6-25 SkillSafetyBench（把 skill 立为独立攻击面）、6-26 AgentDoG 1.5（skill 供应链入侵新叶子）、6-28 Anthropic Agent Skills 概念呼应 —— skill 层的可编程性 / 可复用性 / 可验证性 是 H2 agent 生态的核心。

三组件设计。Buildrix 用一个非常干净的三段架构解决上述问题：

组件形态核心职责解决痛点
CLI · Python 包命令行工具 buildrix开发 / 验证 / 发布 / 安装 / 管理 skill + test caseskill 开发和分发工具缺失
Hub · Web 平台buildrixhub.onrender.com组织 open challenges + reusable skills + test cases + reviews + benchmark leaderboard缺少中央索引和评审场所
本地 agent harnessruntime scaffoldingskill discovery + external toolchain provisioning + progressive context loading + multi-step workflow execution缺少统一的 skill-aware 运行时

skill 包契约（self-contained package）。每个 Buildrix skill 是一个标准化、自包含 的目录，遵循固定结构：

  • 任务指令（instructions.md）—— 用自然语言描述该 skill 处理什么类型任务、输入输出契约、边界条件
  • 可执行脚本（scripts/）—— skill 的核心逻辑，可以是 Python 脚本、shell 脚本、或对外部工具的封装
  • 依赖清单（deps/）—— 运行时需要的第三方库、外部工具链、系统环境
  • 支撑资源（resources/）—— skill 依赖的静态数据、模板、领域知识文件

这个契约的关键设计：skill 是可版本化 的原子对象，可以像 pip 包一样发布、安装、版本管理，避免了当前 agent 场景下"脚本散在 GitHub 上，装完不知怎么用" 的困境。

Golden Test Case 晋升机制。这是全文最有方法论意义的设计。Quantitative test cases 首先由 skill 作者提交，然后经过领域专家（不是 skill 作者本人）审核 —— 一旦被 verify，就晋升为该开放挑战的 golden test case，用于该 skill 及其后续变体的可复现 benchmark 评测。这个机制解决了 agent benchmark 一个根本悖论：如何在没有权威 ground truth 的领域建立可信 benchmark？—— 通过社区专家验证 而非模型自评或作者自证。golden test case 一旦建立，就成为该挑战问题的公共 ground truth，任何后续方法都必须通过它。

本地 harness 的四项能力。本地 agent harness 承担 skill-aware 运行时角色，提供四项 baseline agent 通常不具备的能力：(1) skill discovery —— agent 可以根据当前任务描述在本地已安装的 skill 库里检索匹配 skill；(2) external toolchain provisioning —— 自动安装 skill 声明的外部工具依赖（如 EnergyPlus、OpenStudio 等建筑工程专用软件）；(3) progressive context loading —— 不把 skill 的所有信息一次性塞进 context，而是分阶段按需加载 instructions / scripts / resources，为长上下文任务留出预算；(4) multi-step workflow execution —— 允许 skill 之间组合成多步 pipeline，agent 只需描述目标，harness 负责编排。

Buildrix 把 harness 工程从"单点 harness 设计" 拓展到"领域 harness 生态"，是一个范围扩展 而非拓扑替换。它与 6-30 CUGA FLO 的关系是互补：CUGA FLO 讲"如何在一个 harness 内治理 agent 与 deterministic 引擎"，Buildrix 讲"如何让 harness 与领域社区共同演进"。

建筑工程作为切入领域的理性。建筑工程有几个 agentic AI 生态非常需要的属性：(1) 工作流强结构化（HVAC 模拟、EnergyPlus 输入生成、能耗审计等本身是结构化流程）；(2) 有明确的可验证结果（模拟数值、能耗数值可以定量比较）；(3) 现有工具链成熟（EnergyPlus / OpenStudio / IES-VE 等）适合 skill 封装；(4) 领域专家群体明确，可以承担 golden test 验证的角色。这个"结构化 + 可验证 + 有成熟工具 + 有领域专家" 的四要素组合，可能是其他垂直行业采纳 Buildrix 模式的判断准则。

对你三个研究方向的启发
Harness Engineering（直击毕设）

(1) 把 KV-cache 治理从"单点 harness 内的策略" 提升到"skill-aware harness 层" —— 你的毕设可以借鉴 Buildrix 的三段契约：KV-cache skill 定义（哪种任务用哪种 cache 策略，作为可分享 skill 包）+ KV-cache Hub（把 cache policy 作为社区可分享对象）+ 本地 skill-aware harness；(2) progressive context loading 直接对应 KV-cache 场景 —— 别把整个 skill 一次性 prefill，按指令 → 脚本 → 依赖 → 资源 分阶段加载可显著降低 prefill cost；(3) golden test case 晋升机制 给 KV-cache 评测提供参考 —— 你毕设需要的可复现 benchmark 是不是可以按"作者提交 quantitative case → cache 专家验证 → 晋升 golden case" 的路径建立？(4) self-contained skill 包契约 对 KV-cache 策略非常适用：kv-strategy.md（策略语义）+ scripts/prefill.py（执行）+ deps/（依赖）+ resources/（模板 prompt）；(5) domain toolchain provisioning 直接对应 SGLang 场景 —— harness 自动安装依赖（transformer 版本 / cuda 版本 / SGLang 版本）；(6) 与 6-30 CUGA FLO 的7 hook 原语 组合：Buildrix 提供"skill 生态"层，CUGA FLO 提供"skill 内策略治理"层 —— 双层组合是你毕设最有说服力的架构叙事；(7) Buildrix 的四种能力（skill discovery / toolchain provisioning / progressive context loading / multi-step workflow）都可以在 SGLang 上对偶实现，形成"KV-cache 层 skill-aware harness" 的完整功能矩阵。

Agent Skills Safety

(1) skill 作为原子分发单元 直接连到 6-25 SkillSafetyBench 的攻击面命题 —— Buildrix Hub 就是 skill 供应链，一个 malicious skill 一旦通过晋升机制成为 golden，就会污染整个 leaderboard，因此 Hub 层的 skill audit 机制（Buildrix 目前依赖"专家验证"）是安全设计的核心；(2) Progressive context loading 有安全副作用 —— skill 分阶段加载意味着 agent 在决定使用 skill 时只看到部分描述，恶意 skill 可以把 harmful 逻辑放在 late-stage 加载的 resources 里躲避早期审核；(3) self-contained 包本身是攻击面 —— scripts 目录允许任意可执行文件，deps 允许 pip install 外部包 —— 这是 6-26 AgentDoG 1.5 "Codex/OpenClaw 仓库工件注入" 新叶子的直接对应；(4) domain expert 验证是防线但不是保证 —— 建筑工程专家可以判断 skill 输出是否符合建筑规范，但不一定能审计 script 内的隐蔽后门；后续需要自动化 skill audit（静态分析 + 沙箱执行 + 数据流追踪）作为专家验证的补充；(5) 与 6-30 Action Alignment 的 least privilege 呼应：每个 Buildrix skill 应显式声明它需要的最小权限集（可访问哪些文件、哪些外部工具、哪些网络地址），harness 在执行时对比"skill 声明的权限" 与"用户授予该 harness 的权限 A"，超出即拒绝。

Safety Benchmark

(1) Golden test case 晋升机制 是 safety benchmark 建设的关键方法学参考 —— H1 大量 safety benchmark（DECOMPBENCH / TRACE / AgentSecurityBench）都是作者自证，缺少专家验证晋升的中间层，Buildrix 的三阶（作者提 → 专家 verify → 晋升 golden）是可迁移的；(2) 领域四要素判断准则（工作流结构化 + 可定量验证 + 成熟工具 + 领域专家群体）可以用来判断"下一步该做什么领域的 safety benchmark"：满足这四要素的领域最适合建立可复现 benchmark；(3) Buildrix Hub 是 skill-facing agent benchmark 的天然基础设施 —— 已有 skill 包 + 已有 golden test，把 skill 加上恶意变体或 red-team 版本就可以生成 skill-safety benchmark；(4) progressive context loading 场景的 safety 是空白 —— 当前 agent safety benchmark 假设 agent 一次性拿到全部 skill 信息，但真实 harness（如 Buildrix）分阶段加载，attacker 可以针对不同加载阶段 构造攻击，这是 H2 一个可立项方向；(5) toolchain provisioning safety —— Buildrix 允许自动安装依赖（pip install），这与 6-26 AgentDoG 1.5 的skill 供应链入侵 直接同构，可以针对"依赖劫持" 构造 benchmark 场景；(6) 与 6-30 OSWorld 2.0 组合：OSWorld 2.0 给"长程真实工作流" benchmark，Buildrix 给"skill 生态" benchmark，两者组合覆盖能力 × 生态 两个维度。
