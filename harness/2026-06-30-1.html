摘要（中文翻译，忠实原文）

我们提出流程线束（process harness）—— 一种把遗留工作流提升至Agentic 业务流程管理（Agentic BPM） 而无需替换底层工作流引擎 的新机制。流程线束在确定性工作流引擎 周围放置一个策略治理的 agentic 层，在指定的控制点上拦截，贡献推理、适应与监督能力；与此同时，引擎保留对流程的结构性权威。为了严格定义流程线束，我们开发了 Task-Decision-Flow (TDF) 模型，规定了它的数据 schema 与执行语义。TDF 将 LLM 推理分解为三种受策略治理的智能体类型：TaskAgent 负责知识密集型任务执行、DecisionAgent 负责单案例网关路由、FlowAgent 通过原则化 hook 机制治理运行时流程适应。每个智能体在显式策略下推理，该策略来自流程的 FRAME（治理系统中所有 LLM 调用的聚合策略集）。随后我们提出 CUGA FLO 作为 TDF 模型的设计与实现，并在一个贷款审批工作流 上演示——该案例完整调用了所有三类智能体与hook 驱动的监管覆盖。流程线束独特地协调了：命令式需求（通过 deterministic 工作流执行实现结构合规）与规范性需求（通过策略框定的 agentic 自治在指定控制点实现）。

核心内容解读（TDF 形式化 / FRAME 策略 / 7 hook 原语 / 贷款审批案例）

动机：BPM 工业界 vs Agentic 学界之间的拓扑断层。2024–2026 的 agent 浪潮主要诞生于"LLM 从零搭建系统" 的语境（OpenHands / SWE-agent / Cursor / SuperCoder 都是新建 coding agent）。但工业界事实上存在大量 BPMN 引擎（Camunda / Flowable / IBM Business Automation Workflow / SAP Signavio）已经在跑年龄超过 10 年的关键业务流程：贷款审批、保险理赔、合规审查、订单履约。这些系统的"结构性权威"（哪些节点必须执行、哪些前后关系不可破坏、哪些数据必须落表）是合规和审计的根基，不能被 LLM "一次性重写"。把 agentic 能力 onboard 进这类系统的真正难题是：如何让 LLM 在保留 deterministic 引擎的前提下加入推理、适应与监督？这是这篇 IBM SIL 论文的出发点。

方法：TDF 三元组 + 三类 Agent 形式化。形式上，流程模型 Pm = (V, E) 由起止节点、任务节点 T、分裂网关 G_split、合并网关 G_join 构成。流程知识则是三元组 P = (Pm, Ps, Ph)—— 模型 + 状态（pending/active/hold/completed/halted）+ 历史。TDF 流程线束 TDF_P = (TAs, DAs, FAs) 分别由三类智能体集合组成：

智能体形式定义作用边界
TaskAgenta = (t, C_T, P, Ts, λ)把目标转化为输出，禁止 做批准/拒绝类决策
DecisionAgentd = (g, C_D, P, Ts ∪ {cond_eval}, λ)网关路由 ——强制 先评估条件、再选边
FlowAgentf = (H, Is, φ, C_F(h_k), P, Ts, μ, λ)流程级 hook 干预 —— 跨节点重定向、跳过、添加

每个智能体内嵌一个 LLM 智能体核 λ = (M, Ts, sense, reason, act)。三类 agent 都在显式人类可读策略 下推理，所有策略汇成系统级 FRAME：

F = {C_T(t_i)}_i ∪ {C_D(d_j)}_j ∪ {C_F(h_k)}_k

没有任何 LLM 调用发生在策略边界之外。 双层治理通过访问控制函数 φ: Is → {permitted, prohibited} 实现 —— 这一函数与 hook 策略独立，使"这条 hook 的策略说什么"与"系统允许它实际做什么" 解耦，便于权限管理与策略修改可独立滚动。

7 种 Hook 原语：FlowAgent 的全部干预语义。

操作结构效果语义
continue无按正常边继续
skip_node跳过下一节点节点记录为已跳过
skip_to跳转至任意命名任务节点绕过中间节点（监管覆盖用此原语）
swap_nodes交换两个节点重定向 node_a ↔ node_b
terminate强制停止流程关闭流程实例
remove_node从拓扑移除节点引擎重连前驱与后继
add_node插入新任务节点引擎在当前目标前接入

CUGA FLO 系统架构与 MCP 桥接。核心组件包括：CugaAgent（执行原语 / 中央枢纽）、CugaSupervisor（高复杂度任务编排层）、MCPFlowBridge（FastMCP server / 推理层与执行层唯一通道）、WorkflowEngine（抽象接口；当前实现为 LangGraphWorkflowEngine，把 BPMN 拓扑编译为 LangGraph StateGraph）。MCP 工具注册：FlowAgent 注册 execute_task / route_gateway / evaluate_hook / get_static_config；引擎注册 run_process。运行时分两阶段：Build 阶段 引擎通过 get_static_config 取静态配置编译执行图；Execute 阶段 每个控制点一次往返调用，传递 ControlPointFlowKnowledge。部署结构：config/<process>.bpmn + <app>_config.yaml + supervisor_<app>.yaml 与 policies/task-*.md / decision-*.md / hook-*.md 文件分离 —— 策略是可独立 review 的 markdown 文件，这是 LLM-native BPM 治理的关键产物形式。

贷款审批案例：双源治理 + 可独立审计的执行轨迹。四阶段 BPMN：信用评估 → 审批路由网关 → 贷款/拒绝处理 → 合并。FRAME 包含 4 类策略：

  • Task Policy（信用检查）：产出归一化 credit_score ∈ [0,1]，评分权重 = 还款历史 35% / 债务收入比 30% / 历史长度 15% / 信用组合 10% / 近期查询 10%；明确禁止 task agent 做批准/拒绝决定。
  • Decision Policy（信用网关）：主路由 credit_score > 0.6 → 批准；覆盖规则 loan_amount > 50,000 时阈值升至 0.75。
  • Hook Policy（监管覆盖）：申请人 ID = 4321 受监管限制 → 触发 skip_to 至拒绝处理节点，并写入 rejection_reason = "regulatory_policy_restriction"、policy_override_active = true。
  • Task Policies（结果处理）：贷款处理者 / 拒绝处理者策略 —— 拒绝处理者按 hook 来源走"监管路径"，不引用信用分。

两条执行轨迹清晰展示双源治理：

轨迹申请人credit_score路径结果
正常ID 230.6625TaskAgent → DecisionAgent (0.6625 > 0.6 = TRUE) → Hook continue → TaskAgent 批准loan_granted=true
监管阻断ID 43210.82TaskAgent → DecisionAgent (TRUE) → Hook skip_to → TaskAgent 拒绝处理（监管路径）rejection_reason = regulatory_policy_restriction

关键洞察：DecisionAgent 按信用分（0.82 > 0.6）正确路由 → 批准；但 Hook 根据完全不同的标准（申请人 ID 黑名单）覆盖结果边 → 拒绝。两套策略由独立的 FRAME 子集治理，可独立审计 —— 这正是 BPM 合规要求的核心："谁覆盖了谁、为何覆盖、是否合规" 可被分别追问。

方法学位置：H1 末 harness 第三拓扑。把 6-25 Interplay（harness × post-training 联动）/ 6-26 NOVA（验证联动 / 工业 GMV）/ 6-28 Code Isn't Memory（harness 因果消融）/ 今日 Process Harness（策略治理层 × deterministic 引擎并存）连起来，恰好把 H1 末 harness 工程从"新建系统" 视角推进到"遗留系统嫁接" 视角 —— 这是 H1 末最后一周 harness 谱系的第四节拍。它对 H2 的暗示：越来越多的 harness 论文会从"纯 agent" 转向"agent × 既有 deterministic 子系统并存"，因为这是工业落地的真实形态。

核心数据亮点 / 关键论点
  • 核心论点 ①：harness 工程的第三种拓扑 不是"新建 agent"，而是"agentic 层环绕 deterministic 引擎"—— 这是工业落地的真正形态。
  • 核心论点 ②：用显式人类可读 markdown 策略 文件作为 FRAME 的载体 —— 策略与代码分离，可独立 review、独立修改、独立审计。
  • 核心论点 ③：双层治理 —— FRAME（语义/能力边界）与 access control φ（权限/执行边界）解耦，使"策略变更" 与"权限变更" 可独立滚动。
  • 三类 agent：TaskAgent（执行 / 禁批准拒绝）/ DecisionAgent（路由 / 强制先评估条件）/ FlowAgent（hook 干预）—— 责任分离。
  • 7 种 hook 原语：continue / skip_node / skip_to / swap_nodes / terminate / remove_node / add_node —— 完整覆盖结构性流程变更。
  • FRAME 形式：F = ∪ C_T(t_i) ∪ C_D(d_j) ∪ C_F(h_k) —— 所有 LLM 调用都在 FRAME 边界内。
  • 双层治理：access control φ: Is → {permitted, prohibited} 与 hook 策略独立，便于权限审计。
  • 贷款案例双源：信用分网关（0.6 / 0.75 双阈值） + 申请人 ID 4321 监管 hook 覆盖 —— 两源策略由独立 FRAME 子集治理。
  • MCP 桥接：推理层（LLM）与执行层（WorkflowEngine）通过 FastMCP server 唯一通道交互 —— 解耦清晰可观测。
  • 实现产物：CUGA FLO 在 cuga-project/cuga-agent 仓库 cugaflo 分支已开源，且与 MCP 标准兼容。
  • 命令式 vs 规范式协调：deterministic 引擎实现"结构合规"（命令式），agentic 层在控制点上实现"策略框定的自治"（规范式）—— 两者并存而非互斥。
  • 已知局限：(1) 中间事件 hook 尚未实现；(2) add/remove_node 仅作用于未执行节点；(3) 每 hook 调用 LLM 带来延迟（论文建议缓存 + 轻量预过滤）；(4) FRAME 策略冲突的自动一致性检查仍开放。
对你三个研究方向的启发
Harness Engineering（直击毕设）

本文对 KV-cache / SGLang 毕设的启发角度完全不同于 6-28 Code Isn't Memory：(1) "嫁接式 harness" 的拓扑思想—— 把 KV-cache 治理层视为"agentic 治理层环绕 deterministic 推理引擎"，而非"重写整个 inference runtime"。SGLang / vLLM / TGI 已经是 deterministic 引擎，你的工作不应"覆盖" 它，而应在 KV slot allocation、eviction、prefetch 决策点上放policy-governed agentic hook；(2) 双层治理（FRAME + access control φ） 平移到 KV-cache 即策略层（"该不该 evict 这条 KV"）vs 权限层（"本 tenant 是否被允许触发 cross-tenant prefetch"） 解耦；(3) 策略以 markdown 文件落地，可被 SRE 独立 review—— 这对工业部署的 cache 管理意义重大；(4) 7 hook 原语 对偶 KV-cache 的调度原语集（continue / evict / prefetch / pin / migrate / split / merge）—— 应该枚举出干净的原语集，而非临时 if-else；(5) MCP-style 桥接 暗示 cache 治理层与 inference runtime 应通过显式协议（如 cache_control_v1）交互，便于可观测与多 runtime 兼容；(6) 策略冲突自动一致性检查 是开放问题 —— 你的毕设可在此空白处补 KV-cache 策略冲突的形式化方法（如何证明两条 eviction 策略不会让某条 KV 永远不可达）；(7) Build / Execute 两阶段 对偶 KV-cache 的编译期（schedule plan）/ 运行期（动态调度） 分离 —— 静态 plan 通过 get_static_config 一次拉取，运行期只做控制点调用，能显著降低治理层开销。

Agent Skills Safety

(1) 策略治理 layer 显式化 —— 与 6-30 #2（Action Alignment / least privilege）形成强烈互文：Action Alignment 主张安全应在模型外的 action boundary 强制，CUGA FLO 给出了"action boundary 上的 policy-governed layer" 的具体实现形式（FRAME + 7 hook 原语 + access control φ），这是 Action Alignment 理论的工程模板；(2) 三类 agent 责任分离（TaskAgent / DecisionAgent / FlowAgent）对偶 agent safety 的三类风险面（任务执行风险 / 路由决策风险 / 流程篡改风险）—— 给 skill safety 的责任划分提供了结构对应；(3) 双源治理可独立审计（信用分 + 监管 ID）暗示 agent safety 的规则 vs 模型 应是互补 而非互斥：策略型 hook 处理"明确不可做的事"，模型型推理处理"需要权衡的事"；(4) markdown 策略文件 对偶 safety 的"policy-as-code" —— 安全规则应以可独立 review 的人类可读形式存在，而非埋在 prompt 里；(5) 策略冲突自动一致性检查 直接对应 agent safety 中"helpfulness vs safety" Pareto 优化的形式化（6-28 RUBAS 用 GRPO 隐式优化，本文暗示需要显式 形式化方法）；(6) FlowAgent 的 skip_to / terminate 原语 是 safety guardrail 的正确 abstraction：当检测到危险动作，guardrail 不是改写动作，而是跳转到 拒绝处理节点（写明 rejection_reason）—— 这与 6-30 #2 Action Alignment 的"action boundary 上的 reference monitor" 严格同构。

Safety Benchmark

(1) "嫁接式系统" 的 benchmark 缺口 —— 现有 agent benchmark（OSWorld / AgentBench / SWE-bench）几乎都假设 agent 是新建 系统，缺少"agent × 既有 deterministic 引擎并存" 的评测场景；CUGA FLO 暗示需要"Agentic BPM Bench"（既有 BPMN 引擎 + agentic hook 干预 + 监管覆盖正确性 + 策略可审计性 四维评测），可作为你 H2 毕设另一备选；(2) 策略可审计性指标化 —— 现行 benchmark 几乎没有"策略变更可追溯" 这个维度，本文给出了具体形式：每条策略 = markdown 文件 + 修改历史 + 独立 review；(3) 双源治理 ground-truth —— 贷款案例展示了"两条独立规则的并存与覆盖优先级"，这是 benchmark 设计可借鉴的叠层 ground-truth 范式（不是单一正确答案，而是"策略 A 通过 + 策略 B 覆盖" 的可验证轨迹）；(4) case study 的形式重要性 —— 与 6-30 #3 OSWorld 2.0 的 108 任务相比，本文用一个 贷款案例就完整演示了三类 agent 与 7 hook 原语，说明 BPM 评测可走"少而精的标志案例" 路线（医疗、金融、供应链各 1–3 个标志案例）而非"大量 OSWorld 风格任务"；(5) 命令式 vs 规范式协调 这一区分给 benchmark 设计提供了新维度：评测应分别报告"结构合规率"（命令式：是否完成 BPMN 必经节点）与"策略合规率"（规范式：是否落在 FRAME 内）；(6) MCP 桥接显式化 暗示 benchmark 应直接 audit MCP traffic（推理-执行通道的全部消息），而非只 audit final state —— 这与 6-30 #3 OSWorld 2.0 的"side-effect / bypass" 风险维度形成"嫁接 BPM × 通用 computer-use" 双拼。
