一句话核心贡献
让 agent harness 在 OS 内核层 用 eBPF + IFC DSL 声明并执行策略 —— 首次同时给出路径覆盖 · 语义反馈 · 隔离 的 harness 策略执行方案。
摘要翻译（忠实原文）

AI agent 越来越多通过 harness—— 围绕 LLM 的软件、包括一个执行安全和有效性策略的引擎（如 "commit 之前先运行测试"）—— 在生产环境中运行。执行这些策略需要弥合一条语义鸿沟：策略意图用低规约的自然语言表达，而执行必须作用于具体的系统动作（如运行哪个测试）。许多策略还定义了事件顺序或数据流动作。然而现有方法均有不足：tool-call guardrail 会漏掉绕过工具层的系统动作；OS sandbox 控制资源访问而非动作，且返回不透明错误让 agent 困惑。我们的关键洞察是：策略语境驻留在最接近任务的 agent 内部，而执行必须发生在覆盖所有执行路径的 OS 层。我们提出 ActPlane，一个策略引擎，让 agent 声明策略，并在 OS kernel 中执行、同时给出语义反馈与隔离。ActPlane 使用简单的 信息流控制 (Information-Flow Control, IFC) DSL 支持跨事件策略。我们用 eBPF 实现 ActPlane，并在经验研究策略、coding-task benchmark 和 safety benchmark 上评估。ActPlane 显著提升策略合规性，包括在 tool-call 拦截无法观察的间接执行路径上；开销仅 1.9%–8.4%。ActPlane 开源于 github.com/eunomia-bpf/ActPlane。

核心内容解读（约 550 字）

问题背景：2026 H2 生产环境中 agent 已通过 harness 大规模落地（参考 7-08 Yi/Song Harness MDP · 7-09 Writer AI Harness Effect · 7-10 TTHE 三篇独立证据），harness 的一大核心职责就是执行"commit 前跑测试""不要读 /etc/shadow""敏感数据不要写入日志" 这类 safety + effectiveness policy。但要真正执行策略，必须跨越一条本质性的语义鸿沟——策略是低规约自然语言意图，执行必须落到具体系统调用。作者做了一次实证研究，发现现有两条主流路线都不够用：tool-call guardrail（在 harness 的工具调用接口做拦截）会漏掉 所有 LLM 生成代码直接触发的 syscall（如 subprocess、shell 命令、内联 exec）；OS sandbox（seccomp / SELinux / AppArmor）只控制资源访问权限 而非 动作语义，且失败时返回冷冰冰的 EPERM，agent 完全不知道被拒的业务原因。

核心洞察 + 方法：策略语境在 agent 内 · 执行必须在 OS。ActPlane 让 harness / agent 声明 策略（一条 DSL 语句），policy engine 把它编译成一段 eBPF 程序挂到内核 hook 上（filesystem / process / network / IPC 各层），从而覆盖所有执行路径（LLM 直接生成的 shell 命令、tool 中间的 fork、库函数底层的 open()）都被同一策略约束。关键创新：基于 IFC (Information-Flow Control) 的简单 DSL——可以表达 "数据 X 一旦从来源 A 读取，就不能流向 sink B" 或 "事件 test-run 必须先于事件 commit" 这类跨事件策略（普通 tool-call guardrail 只能做单事件同步检查）。被拦截时 ActPlane 不返 EPERM，而是返回结构化语义反馈（"你想 write 到 X，但当前策略要求先执行 Y"），agent 可以直接读懂并纠正。

与现有工作的突破点：三条独立立场。(1) 相对 tool-call guardrail：ActPlane 覆盖 indirect execution path（LLM 生成的 shell + library 底层调用），tool-call 层根本看不到。(2) 相对 OS sandbox (seccomp/eBPF-only 传统方案)：ActPlane 提供 semantic feedback 与 IFC-based 跨事件 DSL，传统 sandbox 只能 allow/deny 单事件资源访问。(3) 相对 policy-as-code (7-07 Cedar Autoformalization)：Cedar 走 静态形式化验证 路线，ActPlane 走 运行时 kernel 拦截 路线——两者互补：Cedar 编译期证明策略无冲突，ActPlane 部署期保证策略执行。实验：在经验研究策略集 + coding-task benchmark + safety benchmark 上，ActPlane 显著提升合规性（含 tool-call 观测不到的间接路径），overhead 仅 1.9%-8.4%——生产可用。H2 harness 谱系再拓展一格：第十层 · OS 执行层 (Kernel Enforcement Layer)——七层图（学习派收官）+ 经济学层（Writer AI）+ Test-Time 演化层（TTHE）+ 本文 OS 执行层。全代码开源 github.com/eunomia-bpf/ActPlane —— eunomia-bpf 组织已在 eBPF 生态积累多年。

Harness 策略执行三条路线对比 —— ActPlane 是第四条
路线覆盖间接路径语义反馈跨事件策略开销
Tool-call guardrail（主流 harness 内建）❌ 漏抓✅ 有⚠️ 仅工具层低

ActPlane 是首个同时满足覆盖 · 反馈 · 跨事件 三属性的 harness 策略执行方案；且以生产可接受的开销（1.9%-8.4%）实现——这是 harness engineering 落地生产的关键路径。

对研究方向的启发
对 Harness Engineering

H2 harness 谱系再拓展一格 · 第十层：OS 执行层 (Kernel Enforcement Layer)——七层图（学习派收官）+ 第八层经济学层（Writer AI）+ 第九层 Test-Time 演化层（TTHE 7-10）+ 本文第十层 OS 执行层。方法学可复用：(1) "策略语境在 agent · 执行在 OS" 的分层原则——所有需要跨越"NL 意图 ↔ 系统动作" 鸿沟的场景都可套用；(2) IFC DSL 作为 harness 层跨事件策略的标准接口——比 tool-call guardrail 表达力强得多；(3) 语义反馈（结构化告知 agent 被拒的业务原因）应成为所有 harness 拒绝路径的标配，替代传统 EPERM/return -1；(4) 1.9%-8.4% overhead——ActPlane 给"harness 层增加安全 = 显著性能损失" 的偏见画上句号。与 7-08 Yi/Song Harness MDP × TTHE 组"harness 学习 × 演化 × 执行" 三翼。

对 Agent Safety

本文是H2 agent safety 第七派（形式化派 / Policy-as-Code）的运行时侧兄弟——Cedar 走静态编译期，ActPlane 走 OS 内核期，两者拼成"编译期证明 · 部署期执行" 完整闭环。启发：(1) safety benchmark 应显式区分 "静态验证" vs "运行时拦截" 两条路径——ROME / DECOMPBENCH / RUBAS 类 benchmark 目前无法度量 ActPlane 这类内核层 防御；(2) 覆盖间接执行路径 (indirect path coverage) 应成为 safety benchmark 的新元指标——很多 attack success 是通过 subprocess 直接 syscall 绕过 tool-call layer 达成的；(3) 与今日 agent safety 报告 (Boiling the Frog) 形成对偶：Boiling the Frog 展示多轮渐进攻击有 44.4% ASR，其中很多攻击成功的关键是"benign edit + risk edit" 之间的顺序或数据流 已被越过——ActPlane 的 IFC DSL 天然能声明"benign artifact 到 risky sink 的路径不允许"这类跨事件约束。

对 Benchmark

Agent benchmark 必须新增"间接路径 (indirect path) 攻击面"维度——如果 benchmark 的 evaluator 只在 tool-call 层监测行为，就会系统性高估 agent safety。ActPlane 的评估协议（tool-call benchmark + safety benchmark 双侧）给出可复用模板：(1) 报告"tool-call 层观测到的合规率" vs "kernel 层观测到的合规率" 双指标——差值即"tool-call blind spot"；(2) 引入 "IFC violation rate"——数据从来源到 sink 的所有可能路径中，被 taint 违规的比例；(3) 生产可行性维度——benchmark 应报告防御方案的运行时 overhead（如 ActPlane 的 1.9%-8.4%），学术方案不报告开销就无法度量真实部署价值。H2 benchmark 方法学第十一联：路径覆盖联 (Path Coverage League)——benchmark 显式度量"哪些执行路径被观察，哪些没被观察"。
