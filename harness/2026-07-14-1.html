一句话核心贡献
任务难度可以从 model 迁移到 harness —— meta-agent 自动适配的 harness 把 SLM agent 变成 LLM 的 90% 更便宜 替代（4% 成本恢复 89.7% 性能）。
摘要翻译（忠实原文）

前沿 LLM agents 正在自动化众多业务任务，但其高昂的推理成本让大规模部署不可持续。小语言模型（SLM, Small Language Models） 提供了更便宜的替代方案，但当直接放入为前沿 LLM 设计的 harness 中时通常表现不佳。本文表明：对于许多常规业务任务，SLM agent 可以匹敌 LLM 性能，同时成本降低 90%——只要配上一个由 meta agent 自动发现 的适配 harness。关键洞察是：许多任务难度可以从 model 迁移到 harness——通过定制指令 (tailored instructions)、工具 (tools) 与 编排循环 (orchestration loops)。为系统研究这个问题，我们构建了一个把 agent 失败模式 映射到 harness 适配策略 的框架，并搭建了 harness 优化器，它可以从失败轨迹 中自动发现有效的适配。跨 7 个业务导向 agentic 任务 与 3 个 SLM 家族（共 21 个任务-SLM 组合），优化后的 harness 在 16 个 组合上显著提升性能，其中 7 个 关闭了 SLM-LLM 性能差距，且最佳 SLM agent 以 4% 的成本 恢复了 89.7% 的 LLM 性能。进一步分析显示：适配对更多重复性工作流 的任务效果最佳、对具有足够基础能力 的 SLM 效果最佳。这些结果表明 harness 适配可以扩展 SLM agent 在常规业务任务上的实际部署范围。

核心内容解读（约 570 字）

问题背景：2026 H2 生产环境中，agent 部署最大的落地障碍不是"能不能做"，而是"做得起 vs 做不起"——前沿 LLM 单次推理成本让"每客户一个 agent" 的商业模型崩塌。业内的直觉方案是用 SLM（3B-14B）替换 LLM，但 直接换模型只会得到一个残废 agent。本文提出的问题非常尖锐：难道 harness 与模型能力是解耦的吗？ 如果 harness 是为 GPT-5 / Claude Opus 这类前沿模型设计的（假设模型可以自主完成规划、错误恢复、多步推理），那么把 8B SLM 塞进去必然崩溃——因为 harness 隐式依赖了模型没有的能力。作者的关键洞察反过来：许多"任务难度" 是可以在 model 与 harness 之间转移的——通过定制 instructions（把隐式推理显式化）、增加工具（把 SLM 短板外包给 code interpreter / RAG / verifier）、重构 orchestration loops（把长时程推理拆成短步骤 + 显式 state）。

核心方法：从失败模式到 harness 适配的自动化框架。作者不做手工 tuning，而是搭建失败模式 → 适配策略 的映射框架 + meta agent 作为 harness 优化器。具体流水线：(1) 冷启动 把 SLM 放进 LLM harness 收集失败轨迹（fail traces）；(2) 失败分类 meta agent 把失败聚类为可命名的 failure mode（如 "confused by tool signature"、"forgot state between turns"、"over-called browsing"）；(3) 适配策略生成 每个 failure mode 触发对应的 harness 修改（增加 few-shot、拆解 orchestration、添加 verifier）；(4) 迭代优化 应用适配后重新评估，若仍失败则递归。本质是把"人工调参 harness" 变成"meta-agent 自动搜索 harness 空间"。

实验结果与突破：7 业务任务 × 3 SLM 家族 = 21 组合，优化 harness 在 16 组显著提升；7 组关闭 SLM-LLM 差距；最佳 SLM agent 以 4% 成本 恢复 89.7% LLM 性能——即 90% cheaper for ~90% quality。深度分析：适配对更多重复性 workflow 的任务 效果最佳（可提取的模式多），对基础能力足够的 SLM 效果最佳（有底层能力可撬）。H2 harness 谱系再拓展一格：第十一层 · Meta-Optimization 层 (Meta-Agent Harness Discovery Layer)——七层图（学习派收官）+ 经济学层（Writer AI，7-09）+ Test-Time 演化层（TTHE，7-10）+ OS 执行层（ActPlane，7-13）+ 本文 Meta-Optimization 层。与 7-13 ActPlane 组"OS 层执行 × Meta 层发现" 从底到顶完整。哲学突破：不再"给 harness 打补丁"，而是"让 harness 学会自己修自己"——harness engineering 从人工 craft 走向自动 discovery。

SLM Agent 三条路线对比 —— Meta-Agent Harness Adaptation 是第三条
路线成本性能需要什么可扩展性
直接换 SLM 到 LLM harness低（-90%）差（多组合崩溃）无高但无用
手工为 SLM 定制 harness低（-90%）好（若工程师投入足够）专家人工数月低（每个任务从头做）
SLM 微调到具体任务中（训练成本 + 推理低）中-好标注数据 + GPU中（每个任务一次训练）
本文：Meta-Agent Harness Adaptation低（-90% ≈ 4%）好（89.7% LLM）失败轨迹 + meta agent高（跨任务自动化）

Meta-Agent Harness Adaptation 是唯一同时满足"低成本 · 高性能 · 无需人工 · 可扩展" 的路线——这也是 SLM agent 在常规业务任务（有重复性、可 pattern-mine）大规模落地的关键路径。

对研究方向的启发
对 Harness Engineering

H2 harness 谱系再拓展一格 · 第十一层：Meta-Optimization 层（Meta-Agent Harness Discovery Layer）——七层图（学习派收官）+ 第八层经济学层（Writer AI）+ 第九层 Test-Time 演化层（TTHE）+ 第十层 OS 执行层（ActPlane）+ 本文第十一层 Meta-Optimization 层。方法学可复用：(1) failure-mode → adaptation-strategy 映射框架——所有需要"给 SLM 适配 harness" 的场景都可以套用；(2) meta agent 作为 harness 优化器——把 harness 空间的 automated search 变为标配；(3) "任务难度可迁移" 的假设——这是 harness engineering 的第一原理级洞察，值得推广到"prompt engineering 有多少可迁移到 harness"、"tool design 有多少可迁移到 orchestration" 等姊妹问题；(4) 4% 成本 · 89.7% 性能——这是 SLM agent 落地生产的可行性证明，让 SLM harness engineering 从边缘研究变成核心工业问题。下一步预测：Meta-Optimization × ActPlane × Harness MDP 三合一——"发现 harness 结构 + OS 层执行策略 + RL 控制器" 的 end-to-end 自适应 harness system。

对 Agent Safety

本文对 agent safety 的反直觉启发：安全性也可能从 model 迁移到 harness——如果任务难度可迁移，那么"给 SLM 加 verifier / guardrail / structured output" 完全可以补偿其安全边界的欠缺。启发：(1) agent safety 研究应显式区分 "model-level safety" vs "harness-level safety"——RLHF 是 model 层的，ActPlane / RUBAS / verifier 是 harness 层的；(2) SLM safety benchmark 需重新设计——不能直接用 GPT-5 的 harness 跑 SLM 得 unsafe，因为这不是 SLM 本身的问题；(3) meta agent 也可用于 safety adaptation——从 unsafe traces 中自动发现"添加什么 verifier / 加什么 constraint" 能弥补 SLM 的安全欠缺；(4) 与今日 agent safety 报告 (Singapore AISI + Korea AISI Data Leakage) 呼应——AISI 报告发现三个 agent 都不能"完全正确 + 完全安全"，本文提供了工具：用 meta-agent 自动补全 data-handling harness。

对 Benchmark

Agent benchmark 必须报告"harness-adjusted score" 而非 "model-only score"——如果一个 benchmark 用固定 harness 跑不同模型，得到的就是"harness 与 model 的联合能力"，无法区分 model 差异 vs harness 差异。可复用协议：(1) 报告 baseline harness vs adapted harness 双分数——差值即 "harness leverage" (Writer AI, 7-09 引入的概念)；(2) 引入 "cost-adjusted performance"——在同一成本预算下比较不同 model+harness 组合；(3) 提供 "适配上限"——benchmark 应该报告"最好 harness 能把 SLM 拉到 LLM 的百分之多少"；(4) 常规业务任务 vs 创造性任务分开评估——本文发现 harness 适配对重复性任务更有效，benchmark 应该显式区分这两类。H2 benchmark 方法学第十二联：Harness-Adjusted 联——benchmark 从"锁定 harness 比 model" 转向"报告 harness × model 联合空间"。
