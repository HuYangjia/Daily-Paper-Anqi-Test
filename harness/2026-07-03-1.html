摘要（中文翻译，忠实原文）

LLM-as-judge（"grader"）组件现在已是 evaluation harness 的标配，包括那些 pass/fail verdict 会门控下游部署决策 的安全评估 场景。业内广泛假设：把 grader 的 sampling temperature 设为 0 就能让 grading 变得确定性。我们在一个真实的安全评估代码库（Japan AISI 的开源 aisev）上测试这个假设，并揭示它在两个层面上失效。第一层：harness 调用它的 grader 时未设 temperature 也未设 seed，底层 provider 默默应用其默认值 1.0——因此靠近决策边界的 items 在相同的重复运行 中会 pass/fail 翻转（20 次跑内单 item 分歧率高达 ~50%）。第二层：把 temperature 强制 pin 到 0 只能降低翻转而不能消除——在跨 2 个 provider、3 个 model tier、5 种 sampling configuration 的 690 次 API 调用中，7 个 borderline items 里仍有 1-2 个即使在强制贪心解码（top_k=1）下 依旧不可复现。此外，Claude Opus 4.7/4.8 已彻底废弃 temperature 参数——这使传统的主要缓解手段对新一代模型完全不适用。这些发现暴露了一个结构性缺口：只报单跑 verdict、不报方差或grader 分歧度 的评估 harness，可能把噪声当作 safety property 呈现给下游。我们发布一个复现 harness（690 calls · 7 conditions），并建议 harness 把 grader disagreement 作为一等健康指标——与分数本身并列。

核心内容解读（问题 / 双层失效 / 温度废弃信号 / 复现 harness / 结构性建议）

问题背景。2026 年，几乎所有 open-source safety evaluation harness 都用 LLM-as-Judge 做 grader —— 把被测模型输出交给另一个 LLM（往往是同代或更强的模型），让它输出 pass/fail 或分数。这一 pipeline 有一个广泛但未被审计的假设：只要 grader 的采样温度设成 0，grading 就是确定性的，可以拿单跑结果作为 safety verdict。这个假设的直接后果 是——业界大量 safety evaluation 论文只跑一次，然后把单跑分数写进摘要与 leaderboard。作者选中 Japan AISI（日本 AI 安全研究所）的开源代码库 aisev 作为真实攻击面——不是玩具 demo，而是一个会决定日本国家 AI 部署门槛 的现役 harness。

双层失效结构。本文最有工程学价值的一段是把 grader 的 non-reproducibility 拆成两层——每一层都是可独立复现的失效模式：

层级触发条件观察严重度
层 ①harness 调用 grader 时未显式设置 temperature / seedProvider 默认 temperature=1.0；边界 item 在相同 20 次重跑 内 pass/fail 翻转率高达 ~50%严重
层 ②Pinning temperature=0，甚至进一步 top_k=1 强制贪心7 个 borderline items 中仍有 1-2 个 non-reproducible（跨 690 calls × 2 provider × 3 tier × 5 config）结构性
层 ③（元）模型代际更新Claude Opus 4.7 / 4.8 已废弃 temperature 参数——传统主要缓解手段直接失效范式转折

层 ① 说明harness 工程失误 —— 大量 harness 从未显式设过 temperature，靠 provider 兜底但 provider 默认是 1.0。层 ② 则更严重：即便工程师做对，物理层面仍存在 non-determinism（如 batching、GPU 非确定性、prefix caching、MoE routing、KV-cache 精度差异），温度=0 只削减了采样分布，未削减底层 backend 的实现层随机性。层 ③ 是最有前瞻性的一击：Claude Opus 4.7 / 4.8 已不接受 temperature 参数—— 说明业界主流缓解手段（"pin temp=0"）在新一代模型上直接过时。

为什么温度=0 是"必要非充分"？作者把这个命题写进标题。数学上：如果 grader 有多个"接近最优" 的判断路径，即使贪心解码，只要浮点非结合性 / batching 顺序 / KV-cache 精度 / GPU 非确定性任一发生变化，输出 token 都可能切换到另一条路径——这在 pass/fail 边界 item 上表现得最鲜明，因为这些 item 本身信号弱。因此，temperature=0 降低但不消除 —— 是 necessary（去掉能立刻变差）却 not sufficient（做了也无法证明确定性）。

复现 harness 的贡献。作者释出 690 调用 × 7 条件 的复现 harness —— 提供固定 prompt / 固定 grader / 五种 sampling config，让任何团队直接跑就能复现 non-determinism 曲线。这对社区有三条即时价值：(a) H2 所有做 LLM-as-Judge 的 safety harness 都可以把它作为回归测试；(b) provider 侧（OpenAI / Anthropic / Google）可以用它作为SLA 度量 —— 承诺"边界 item 20 次重跑 disagreement < X%"；(c) 学术侧可以用它标定"哪些 borderline items 是 grader-noise 主导"，把这些 items 从主 leaderboard 剔除或加权。

结构性建议：grader disagreement 作为 first-class 健康指标。本文最有影响的建议是：evaluation harness 应把grader disagreement 与方差 作为一等健康指标，与分数并列报告——不再允许"单跑 verdict 上榜"。作者建议 harness 应至少报告：(1) 单 item 的 K-run disagreement rate（K 默认 = 20）；(2) 每条 borderline item 的 flip probability；(3) 每个 grader × config 组合的 reproducibility class（deterministic / stable / unstable / unusable）；(4) 每份 leaderboard 报告应带grader-disagreement 附录——供审稿人核对。

与 7-02 IRT-Safety 的呼应。本文与 7-02 IRT-Safety（Efficient Safety Benchmarking via Item Response Theory · arXiv 2606.20626）构成正交但互补的 harness 方法学升级：IRT 讲"物品侧信息经济学"——哪些 item 值得跑；本文讲"评委侧可靠性"——同一 item 跑多次也未必同答。两者合起来定义benchmark reliability 二维图：横轴 item informativeness（IRT）× 纵轴 grader stability（本文）——理想 benchmark 应在两轴都做审计。

三条 harness 工程反模式。本文隐含指认了三条社区当前流行但结构上有问题的做法：(a) "只调 grader 温度不查 provider 默认"——很多 harness code 里 call_llm(prompt) 直接调用，把 temperature 交给 provider 兜底；(b) "单跑 verdict 上 leaderboard"——不报方差就是噪声当作 safety；(c) "相信温度=0 = 确定性"——这个假设从来没被真正测过，只是 folklore。

Harness Engineering（直击毕设 · 与 KV-cache 高度关联）

(1) 本文的三条"non-determinism 来源"里，KV-cache 精度差异、prefix caching、batching 顺序都直接指向你 SGLang 侧的毕设方向——KV-cache reuse 不是简单的性能优化，它本身就是 grader 非确定性的一个物理来源。这意味着你的毕设可以做"KV-cache reuse 对 grader verdict 稳定性的因果影响"实证研究，用本文的 690-call 复现 harness 作为标定平台；(2) 把"cache-hit 判定"做成五级 reproducibility class——像本文对 grader 的分级一样：deterministic（完全相同 token 输出）→ stable（相同 verdict）→ unstable（边界翻转）→ unusable（超阈值分歧）；SGLang cache manager 可根据下游任务的 verification ladder 层级（对应 7-02 loop engineering）决定"能 reuse 到哪一级"；(3) KV-cache 缓存决策必须并入 harness disagreement 报告 —— 你的毕设可以把"本次运行的 cache-hit 率、cache eviction 事件、精度类型（fp16/bf16/fp8/int8）" 作为 harness metadata 一起写入 leaderboard 报告，让下游研究者能追溯 grader disagreement 是否由 cache 造成；(4) Claude Opus 4.7/4.8 废弃 temperature 恰好是你 KV-cache 论证的结构性支持 —— 未来 harness 无法再靠"调低温度" 掩盖 non-determinism，必须直面 backend / cache 层的随机性；(5) 与 7-02 Loop Engineering 的autonomous-zone verify 组合：loop verification 越自主，grader disagreement 越致命——因为 loop 会自主前进 而不停下让人复核；因此 loop specification 的 verification 组件必须要求 grader-stability class ≥ stable；(6) 你可以把毕设包装为"KV-cache-aware evaluation harness"：给 SGLang 加一层 harness middleware，自动记录 cache stats × grader verdict，输出 disagreement report；(7) 对 CFS 迁移的项目也有联动 —— logits_dump 场景 天然对应"harness disagreement 复盘" 需求，可以把 dump 出来的 logits 作为 grader stability 的物理证据（"相同 prompt 不同 batch 序 → logits 差异 → verdict 翻转"）。

Agent Skills Safety

(1) Grader disagreement 是 agent safety monitoring 的隐藏漏洞：现在很多 agent safety pipeline 用 LLM-as-Judge 做实时行为监控（judge 每步 action 是否安全）；如果 judge 本身在边界翻转率高达 50%，那么 agent 的"safety verdict"从一开始就是噪声 —— 这与 6-30 Action Alignment / 7-01 Epistemic Property / 7-02 Why Generalize 三派立场组成 agent safety H2 四派：外置派 · 认知派 · 泛化派 · 评委派（本文）——第四派专门讨论"safety 判定过程本身的可靠性"；(2) Prompt injection defense benchmarks 都用 LLM-as-Judge，本文的结果意味着"我们衡量 defense 效果" 本身也不可靠——H2 应有 defense-benchmark reproducibility audit；(3) 对 skill-facing attack surfaces（如 SkillSafetyBench）：Skill 的 safe/unsafe 判定极度依赖 grader，本文数据说明skill-level safety 分数 至少需附K-run variance；(4) Claude 4.7/4.8 废弃 temperature 直接影响所有红队工具 —— 传统的"低温度稳定攻击" 假设不再成立，H2 攻击方也要重新校准；(5) 与 evaluation awareness（6-22 Nayan 等）组合：模型检测到自己在被测 → 采取不一致行为；本文说 grader 本身也不一致——两侧同时不确定，safety verdict 的信息量 大幅下降；(6) 立即可用：agent safety 研究者应把K=20 重跑 disagreement 报告 纳入 red-team 报告标准。

Safety Benchmark

(1) H2 所有 safety benchmark 都应加 grader-reproducibility 附录——AIR-Bench / HarmBench / SafetyBench / TrustLLM / AgentBench 全线适用；(2) 与 7-02 IRT-Safety 构成 benchmark reliability 二维审计：横轴 IRT 物品信息量 × 纵轴 grader disagreement rate——理想 benchmark 在两轴都做审计，且剔除同时低信息量 + 高 grader 分歧的 items；(3) 本文的690-call 复现 harness 直接可作为其它 safety benchmark 的回归测试基座——把自己 benchmark 的每条 borderline item 塞进这套 harness 跑一遍，量化reproducibility class；(4) 立即可创建的新 benchmark：Grader Stability Benchmark——收集 100+ borderline items × 10+ grader 模型 × 5 config × 20 runs，公布"每个 grader 在哪些 item 上翻转"表格；(5) Provider SLA benchmarks——把"disagreement rate < X%" 立为 provider 应披露的产品性能指标，就像现在披露 latency / cost 一样；(6) 与 6-28 REALM / 6-26 ForesightSafety-VLA / 6-30 OSWorld 2.0 组合：输入侧穷举 × 物品侧 IRT 精选 × 评委侧 disagreement 审计 ——2026 H2 safety benchmark 的三层可靠性架构；(7) 长期看，本文的启发是safety benchmark 的可靠性论文本身 应成为独立子领域 —— 就像统计学里的"meta-analysis of measurement error"；(8) 值得关注的伴随成果：论文用真实国家级 harness 作对象（aisev），说明该问题已经进入监管视野——预计 H2 会有 NIST / UK AISI / Japan AISI 联合发布 harness 可靠性最低标准。
