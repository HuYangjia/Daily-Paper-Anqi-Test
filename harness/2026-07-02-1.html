摘要（中文翻译，忠实原文）

2026 年中期，一句口号重新组织了从业者谈论 coding agents 的方式：停止 prompt 你的 agent，开始设计 prompt 它的 loop。本文把这个 claim 严肃对待并给出仔细处理。我们把这个新实践的对象称为 loop specification：一个有界、可复用的工件，由 trigger（触发器）、goal（目标）、verification step（验证步骤）、stopping rule（停止规则）、memory（记忆） 构成，由人类交付给 agent harness（如 Claude Code 或 Codex），让 agent 自主追求目标——替代 逐步 prompt。我们把这个外部 loop specification 与两件事拆开：(a) 普通编程 loop；(b) harness 已经作为 plumbing 提供的内部 perceive-act-observe 循环。我们把 loop engineering 定位为 prompt → context → harness → loop 演进图上的新一层；并反对"loop 替代 prompt" 的强口号——loop 与 prompt 是不同工具 且各有用途。我们贡献四点：(1) 学科的定义与范围；(2) 围绕 trigger / goal type / 五级 verification ladder / architecture / 命名 terminal states 组织的 loop specifications 的解剖与分类学；(3) Loop Library 语料——五十个真实 loops 的公开语料，手工编码；(4) 基于自我修正、reward hacking、model-as-judge fragility 文献的设计原则与反模式。语料显示：70% loops 在 ladder 的 autonomous zone 中 verify · 74% 命名 terminal states，但自动化 triggering 与 durable memory 相对欠发达。文末讨论必须尊重的限制：verification 负担、comprehension debt、cognitive surrender 风险。

核心内容解读（问题 / loop 与已有概念的边界 / 五元组契约 / 分类学 / Loop Library 数据洞察）

问题背景。2026 年中期起，"stop prompting your agent, start designing the loop that prompts it" 这句口号在开发者社区扩散，但它的技术对象 一直没有被形式化——"loop" 到底指什么？是普通编程 loop 吗？是 agent harness 内部的 perceive-act-observe 循环吗？还是别的东西？本文的贡献首先是拆掉概念混淆：明确把外部人类递交给 harness 的 loop specification 从"编程 loop"和"harness 内部循环 plumbing" 中区分出来。前者是规格，后者是实现；前者由人类工程师撰写，后者由 harness 厂商内置。

层级演进图。作者把 agent 工程的历史演进画成四层图：

核心命题是：loop engineering 不淘汰 prompt engineering——loop 与 prompt 是不同工具：prompt 用于"一次性内容生产"，loop 用于"自主目标追求"。作者特别反对社区中强版的"loop 淘汰 prompt" 论。

五元组契约。本文最有工程学价值的一段是把 loop specification 形式化 为一个有界、可复用的工件，由五个组件组成：

  • trigger（触发器）：何时启动这个 loop？—— 可以是手动、定时、事件驱动、条件驱动。语料显示自动化 triggering 显著欠发达——大多数 loops 目前还是手动或简单事件触发。
  • goal（目标）：这个 loop 要达成什么？—— 分类为多种 goal type（fact production / state achievement / continuous monitoring / iterative refinement 等）。
  • verification step（验证步骤）：如何知道已经达成？—— 这是全文最重要的组件（见下 verification ladder）。
  • stopping rule（停止规则）：什么条件下必须终止？—— 与命名 terminal states 联动（success / failure / timeout / budget-exceeded / manual-abort 等命名状态）。
  • memory（记忆）：跨迭代 / 跨 session 保留什么？—— 语料显示durable memory 相对欠发达，多数 loops 靠 harness 提供的临时 context，缺少显式跨会话的 memory 契约。

五级 Verification Ladder。本文的另一个方法学核心 是把 loop 的验证组织为五级阶梯——从最弱到最强：(1) human-only（每次迭代由人验证）→ (2) cheap-checks（语法、格式、shape 校验）→ (3) strong-verifier（外部程序如编译器、单元测试）→ (4) autonomous-zone（loop 自身可执行 model-as-judge 或形式化验证并自主前进）→ (5) self-consistent（多样本自洽 + cross-verification）。语料 70% loops 已进入 autonomous-zone——说明社区实践确实已经把验证做到了"loop 可以自主前进不用人干预"的水平；这个数字也反证了"loop engineering 是真实的实践"，不是纯理论。

命名 Terminal States。74% loops 命名了终止状态——这是从"循环无边界地跑到超时" 时代升级到"每个 loop 有语义化 stop code" 时代的标志。命名 terminal states 有三个好处：(a) 可审计（stop code 就是审计追溯的起点）；(b) 可组合（外层 loop 可根据内层的 terminal state 分派不同分支）；(c) 可对齐（用户对"完成" 的期望被明确写下）。

三条限制警告。作者不做 loop 万能论。文末警告三条实践必须尊重的限制：(a) verification burden——loop 每 iteration 都要 verify，验证成本可能压死 loop 本身；(b) comprehension debt——loop 越自主，人类越难理解它到底跑到了哪一步；(c) cognitive surrender——把太多决策外包给 loop 后，人类失去关键判断能力。这三条构成了 loop engineering 学科的伦理边界。

Harness Engineering（直击毕设）

(1) 把 KV-cache 决策从"harness 静态策略" 升级为"loop specification 的 memory 组件" —— 你的毕设不必把 cache 策略埋在 harness 里，而是让每个 loop 显式声明"它需要什么 memory 契约"（长期 KV / 短期 activation / 无状态），loop-runtime 据此决定 cache 策略；(2) 五级 verification ladder 可以直接映射为"KV-cache 有效性验证" 的五级：hash 一致（cheap）→ prefix embedding 相似（strong）→ downstream task pass（autonomous）→ multi-sample consistent（self-consistent）——为 cache reuse 建立分级信任 机制；(3) 命名 terminal states 对应 KV-cache 的命名 eviction 事件——"budget-exceeded / dependency-invalidated / manual-flush / stale" 四类命名状态可以让 cache 决策可审计；(4) automated triggering 欠发达 恰是 cache prefetching 的机会窗口——如果 loop 声明了下一步会触发什么 skill，cache-manager 可以预取 该 skill 的 KV；(5) durable memory 欠发达 对应 跨 session KV persistence——你毕设可以做"把 loop 的 memory 契约翻译为 KV-cache 持久化策略" 的编译器；(6) 与 6-30 CUGA FLO 的 7 hook 组合：CUGA FLO 的 hook 是"harness 内策略"，loop specification 是"harness 外规格"——你的毕设可以把 KV-cache 决策做成"loop-declared, hook-enforced, harness-executed" 三层架构；(7) verification burden 直接对应cache verification 开销——如果每次 cache hit 都要重跑全 pipeline verify，reuse 收益就被吃掉；因此需要"基于 ladder 分级" 的分层 cache verification 而不是全走 autonomous-zone；(8) 与 7-01 Buildrix 的 self-contained skill 组合：skill 包 = self-contained 内容，loop specification = self-contained 意图，两者共同定义 SGLang 侧的可移植性契约。

Agent Skills Safety

(1) loop-level attack surface 是 H2 未被探索的空白 —— 目前 agent safety 讨论集中在 skill / tool / prompt 层，但 loop specification 本身可以被污染：malicious trigger（假事件触发敏感 loop）/ malicious stopping rule（永不停机的 loop 消耗资源）/ malicious memory（跨 session 沉淀 exfiltrated 数据）；(2) 五级 verification ladder 直接映射为 safety verification 的分级信任 决策：low-risk goals 可以停在 cheap-checks，high-risk goals（e.g. 涉及金融、删除、外发）必须走 self-consistent；(3) 命名 terminal states 天然对应 safety incident 报告——每种命名 stop code 对应一个可追溯的 safety 事件类型；(4) cognitive surrender 警告 是 agent alignment 中长期人类监督衰退 命题在 loop 层的显式表述——与 7-01 的 Epistemic Property / Teachability 概念（"保留 corrective leverage"）方向一致；(5) automated triggering 欠发达 在 safety 侧是好事——一旦大规模自动触发普及，attacker 可以通过"制造事件" 远程激活敏感 loop（例如伪造 CI 失败触发部署 loop）；因此本文给trigger authentication 立了立项理由；(6) 与 6-30 Action Alignment 的 least privilege 呼应：每个 loop specification 应声明"它需要的最小 authority 集"，harness 在启动 loop 时对比"loop 声明的权限" 与"用户授予该 harness 的权限 A"，超出即拒绝；(7) Loop Library 语料 直接可以做loop-level red-team benchmark——把 50 个 loops 每个都拿出来做恶意变体，是现成的 H2 evaluation 起点。

Safety Benchmark

(1) Loop-level agent benchmark 是空白 —— 现有 agent benchmark（OSWorld / AgentBench / TAC / STAGE-Claw）都用"一次性任务 + 步数上限" 评测，缺少"agent 面对递交给它的 loop specification 时的可靠性" 评测维度；本文的Loop Library（50 loops）就是loop-level benchmark 的天然起点；(2) 五级 verification ladder 可以作为 benchmark 中验证信任级别 的量化维度——同一个任务在不同 ladder 级别下的通过率差异揭示模型的验证成熟度；(3) 命名 terminal states 可以作为 benchmark 的结果分类维度——不再是二元 pass/fail，而是五类 stop code 的分布（success / failure / timeout / budget-exceeded / manual-abort）；(4) verification burden 量化 是 benchmark 应报告的关键 economics 数据——每次通过所需的验证 tokens / verification calls / wall-clock，这是现有 benchmark（OSWorld 2.0 之外）普遍不报的维度；(5) automated triggering + durable memory 欠发达 恰是benchmark 建设的机会窗口——直接构建针对这两个维度的 benchmark（如"trigger-race conditions"、"cross-session memory-consistency"），H2 应该会有多篇 follow-up；(6) 与 6-28 REALM / 6-26 ForesightSafety-VLA 组合：REALM 覆盖"感知层 red team"，本论文覆盖"loop 层 red team"——两者组合成"感知 × 循环" 双侧统一的 benchmark 矩阵；(7) Loop Library 手工编码 也给 benchmark 建设立范：50 loops · 每一条都手工编码——比 LLM 生成 case 更有可信度，与 7-01 Buildrix 的golden test case 晋升机制 呼应；(8) cognitive surrender 长期人类监督衰退可以成为 benchmark 的过程指标——比如"agent 连续跑 100 iterations 后人类干预率"作为长期 safety 指标。
