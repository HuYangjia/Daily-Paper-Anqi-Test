一句话核心贡献
把"结构化索引 vs agentic grep" 这个被 coding-agent vendor 默认默认的问题做成可重复的因果消融——在同一 Claude Opus 4.7、同一沙盒、同一 leak-audited 评分器下，仅在工具 schema 中加/去 codebase_search 与 codebase_graph 两个工具，Loc acc@5 44.3% → 84.5%（+39.6 pp，p<0.0001）、Resolve 41.9% → 50.4%（+7.9 pp，p=0.003）、$/solved $2.84 → $2.30，且收益集中在 3+ 文件改动（91.3% vs 44.9% 定位率），为 harness 工程提供首个harness-control 实验范式 的开源模板（per-cell 数据库 + leak-audit 脚本全部释出）。
摘要（中文翻译，忠实原文）

Coding agent 现在把 LLM 与工作仓库上的检索 交织在一起，而检索的具体实现方式在已部署的各种 harness 之间差异巨大。在一个固定的 coding-agent harness、固定的模型上，给它加一个结构化代码库索引 到底会不会改变成本或 resolve 率？我们跑了三个 arm（含索引的 harness、同一 harness 不含索引、以及一个 agentic-grep 对照 harness），在 SWE-PolyBench Verified 和 SWE-bench Pro 上，全程固定 Claude Opus 4.7，跨三个 seed，每个任务在泄漏审计过的 per-task sandbox 中运行。

同 harness 内的消融 产生了一个很大的定位率提升和一个具有统计显著性的 resolve 率提升，单 cell 没有成本惩罚，每个解决方案的成本反而更低。跨 harness 对照 显示，相对于 agentic-grep baseline，索引在 resolve 与定位上没有退步，仍然没有成本惩罚。我们释出了 per-cell 排除账本、leak-audit 脚本、定位提取器和结果数据库。结构化代码库索引的部署问题因此不再是"是否太贵以至于跑不起"（跨 seed，索引方案的 $/solved 都比 agentic-grep 更低），而是工作负载是否包含多文件改动——结构化排序在这种场景下才会真正回本。

核心内容解读（三 arms 因果消融 / 三索引设计 / 多文件回本曲线）

动机：检索差异被 vendor 默默吞掉，缺一个因果对照。2024–2026 H1 的 coding agent 路线分歧严重：Cursor / Cline / Aider 走 PageRank-ed repo map；Cody / SuperCoder 走 AST + 嵌入 + 图三索引；OpenHands / OpenCode / Aider+ 走"grep 就够了"。Sen et al. (NeurIPS 2024) "Is grep all you need?" 在 agentic loop 内对比 grep 与 dense retrieval 后倾向 grep，但其设定是非代码。在代码场景，结构化索引的工程成本不低（AST 解析 + 嵌入 + 图构建 + 增量更新），如果对 resolve 与成本都没增益，那 vendor 投入索引基建就只是"看上去专业"。这篇论文正面回答这个问题。

实验设计：harness-control 的因果消融范式。三个 arm，仅工具 schema 不同：

Arm组成对照角色
SC-ONSuperCoder harness + codebase_search + codebase_graph含索引的实验组
SC-OFFSuperCoder harness 去掉仅 上述两个工具，其余完全相同同 harness 内因果对照组

统一变量：模型固定 Claude Opus 4.7、同一沙盒、同一 leak-audited 评分器、3 seed、pass@1。基准：SWE-PolyBench Verified（多语言）+ SWE-bench Pro（长上下文 Python），共 91 实例（Go 34 + Java 20 + Python 37）。配对样本：SC-ON vs SC-OFF n=80；SC-ON vs OpenCode n=78；三方交集 n=75。这是 coding-agent harness 论文里第一次把"同 harness 因果消融" 与"跨 harness 对照" 写进同一篇文章。

这是 harness 工程链条第一次给出"索引收益与改动跨度成正相关" 的定量曲线。结论：部署索引的决策不再是"是否太贵"，而是"工作负载里有多少 multi-file change"。

三索引设计：Vector + Graph + BM25 三轨并行。(1) Tree-sitter 解析每个文件 → AST；(2) 提取器遍历 AST 收集 definitions / identifiers / references / call edges；(3) 代码 chunk 嵌入为向量；(4) 三索引并行填充：Vector index（语义召回）、Graph index（call 边可达性）、Lexical BM25 index（精确符号召回）。增量更新通过 Merkle-tree diff：编辑只让受影响 chunks 失效重索引，而非整个仓库。Agent 拿到两个工具：codebase_search(query, strategy={vector|lexical|graph|hybrid}) 与 codebase_graph(symbol, direction)—— 后者按符号遍历 call graph 返回 callers/callees。这是 harness 工程里第一次把"检索策略" 作为 agent 的显式参数 暴露，而非藏在 vendor 黑盒里。

方法学位置：harness-control 实验范式三联拍。把 6-25 Interplay（harness × post-training）/ 6-26 NOVA（verification 联动）/ 今日 Code Isn't Memory（因果消融）连起来，刚好补齐 H1 末 harness 工程的三个抽象层级：训练侧（如何让 harness 与 post-training 联动）+ 验证侧（如何让 verifier 既是 gate 也是梯度）+ 实验方法学侧（如何科学评估一个 harness 组件）。前两篇给"怎么做"，这篇给"怎么测"——这是 vendor 文化（"我们就该有 index"）与学界文化（"先做 ablation"）之间长期缺失的桥梁。

核心数据亮点 / 关键论点
  • 核心论点 ①：harness 组件研究应该做成因果实验—— 同模型 × 同沙盒 × 同评分器 × 仅工具 schema 不同。
  • 核心论点 ②：结构化代码库索引 ≠ "memory"—— 它是外置的、可被 leak-audit 验证的 检索基建，不被 vendor 黑盒化。
  • 核心论点 ③：索引收益集中在 multi-file change—— 决策因子从"太贵" 转向"工作负载分布"。
  • Resolve（pass@1）：SC-ON 50.4% > OpenCode 45.3% > SC-OFF 41.9%（n=80 配对 p=0.003）。
  • Loc acc@5：SC-ON 84.5% >> SC-OFF 44.3%（+39.6 pp，p<0.0001）—— 定位是结构化检索最强项。
  • 3+ 文件子集：定位 91.3% vs 44.9%—— 多文件改动是索引回本的拐点。
  • $/solved：$2.30 < $2.84 < $2.92—— 索引非但不贵，反而 cheaper-per-solve。
  • $/cell 不显著：p=0.73—— 优势来自更高 resolve，不是更低单次成本。
  • Turns 减少 8.3（p<0.0001）—— 索引帮 agent 少绕弯。
  • 三索引：Vector（语义）+ Graph（call 边）+ BM25（符号精确）+ Merkle-tree diff 增量更新。
  • 跨 harness 对照：SC-ON 略优于 OpenCode（resolve / acc@5 方向一致 p=0.087/0.080）—— 索引不会让 agent 退步到 agentic-grep 之下。
  • 开源：per-cell 排除账本 + leak-audit 脚本 + 定位提取器 + 结果数据库全部释出。
对你三个研究方向的启发
Harness Engineering（直击毕设）

这篇是"如何科学评估一个 harness 组件" 的开源模板，对你 KV-cache / SGLang 毕设的启发极具操作性：(1) 因果消融范式——把每个 KV-cache 组件（eviction / placement / prefetch / sparse pattern）当 codebase_search 一样处理：固定模型、固定 workload、固定评分器，仅 切换该组件开/关，做配对 Wilcoxon 检验；(2) leak-audit 思想—— KV-cache benchmark 的 hidden leakage 是"跨 request 的 cache 残留"，应该写出 per-task sandbox 隔离脚本并 release；(3) per-cell ledger—— 把每个 (task, seed, config) 三元组的成本/延迟/吞吐写入数据库，而非只 report aggregate；(4) multi-file 拐点 对偶 KV-cache 的multi-request 拐点—— 长上下文/多 turn/multi-tenant 才是 cache 设计回本的场景，benchmark 应该按 request 跨度分桶；(5) 三索引并行（Vector + Graph + BM25）对偶 KV-cache 的三策略并行（LRU + Semantic + Prefetch hint）—— 不要把任何一种 cache 策略作为"正确答案"，让 agent 在 runtime 显式选择 strategy 参数；(6) 3 seed × paired Wilcoxon—— 这是你做毕设实验时强烈推荐采用的统计方法，比单一 mean 更能 defend。

Agent Skills Safety

这篇对 agent safety 研究有方法学层面启发：(1) 同 harness 因果消融 是评估 safety 干预效果的正确实验范式—— 当前 safety alignment 工作（如今日 #2 RUBAS）常把"训练数据 + 训练方法 + 评测 backbone" 三件事混在一起，应学习这篇做仅切换单一干预 的 ablation；(2) per-cell ledger 对偶 safety 的 per-trajectory ledger—— ASR 平均数会掩盖少数高危轨迹，应释出每条轨迹的 safety violation 标签；(3) multi-file 收益曲线 对偶 safety 的multi-turn 收益曲线—— 6-25 SkillSafetyBench 已指出多 turn 才暴露 skill-mediated 攻击，今日这篇提供了"按 horizon 分桶报告" 的可视化模板；(4) leak-audit 脚本 对偶 safety 的prompt-leakage audit—— 应释出"测试集是否在训练集出现过" 的脚本，让 safety 评测可复现；(5) 结构化索引 vs grep 对偶 safety 的外置 guardrail vs 内嵌 alignment—— 同 backbone 下到底外挂 Llama-Guard 还是 RLHF 重训，应该做 same-experiment-design 的对比，而非各报各 ASR。

Safety Benchmark

这篇为 safety benchmark 设计提供了一套"实验方法学最小模板"：(1) 固定 backbone—— Safety benchmark 应该至少 report 1 个 fixed-model 的全量 ablation，否则跨 paper 的 ASR 数字无法比较；(2) per-cell ledger—— 释出每个 (task, seed, defense) 三元组的原始结果，否则后续 paper 无法做 meta-analysis；(3) leak-audit 脚本—— Safety benchmark 的最大 confounder 是 prompt-leakage，应必备此脚本；(4) 3 seed × paired Wilcoxon—— Safety benchmark 不应只 report 一个 mean ASR，应给出配对置信区间；(5) "$/solved" 思想 平移到 safety 即 "$/blocked"—— 防御方法的真实成本应按"每成功拦截一次攻击的成本" 报告；(6) multi-file 分桶 对偶 safety 的multi-turn 分桶 + multi-tool 分桶—— 评测应按 horizon 与 tool diversity 切分；(7) 与 6-26 ForesightSafety-VLA 的"L × W × V 三轴诊断" 形成跨方向的同构框架：harness control 是方法学层面，VLA L×W×V 是语义层面，两者都把单一 ASR/Success 数字分解成多维诊断矩阵。
