一句话核心贡献
Automatic harness evolution 的性能增益可能是"额外 search 预算" 的假象——在匹配预算 与 held-out 任务 下并未 consistently 胜过简单 test-time scaling。
摘要翻译（忠实原文）

我们重新审视 LLM agent 的 automatic harness evolution 评估。既有的 harness evolution 方法用单元测试样例 搜索 harness 配置，然后在同一个公开 benchmark 上报告最终性能。这个协议提出了两大根本性顾虑。第一，harness evolution 本身就是一个迭代搜索过程：反复评估 · 用任务反馈修改候选 harness——正如 agentic test-time scaling 一样，它应该在匹配 feedback 预算与 inference 预算的条件下与简单的 task-level search baseline 比较，才能判定"增益来自更好的 harness 设计" 还是"仅仅来自额外搜索"。第二，因为搜索和最终评估共用同一 benchmark，所报告的增益有过拟合到该特定任务集的风险。为此，我们进行了大规模对比评估：把 harness evolution 与简单 test-time scaling / discovery baseline 在同等 feedback 与 inference 预算下比较，并在 held-out 任务 上评估演化后的 harness 以判定改进是否泛化。Terminal-Bench 2.1 × GPT-5.4 与 Claude Opus 4.6 的实验表明：automatic harness evolution 未能 consistently 胜过简单的 test-time scaling 方法，且表现出有限的泛化性。我们的结果对 automatic harness evolution 的实际效力提出了重要问题，也凸显了为 automatic harness design 建立更公平的评估协议与 benchmark 的必要性。代码开源。

核心内容解读（约 580 字）

问题背景：过去两个月 H2 harness 谱系急速膨胀——从 CMU Kästner 组 Meta-Agent Harness Discovery（7-14 报告，我们把它列为第十一层 Meta-Optimization 层）、到 Nie/Zhang 组 TTHE test-time 演化（7-10 报告，第九层）、再到 Yi/Song 组 Harness MDP（7-08 报告，学习派收官）——整个方向都在争先恐后地宣布"我们的 harness 自动化更好"。本文一石激起千层浪：你们的评估协议本身站不住脚。作者指出两个隐藏 bug：(1) 搜索预算未对齐——harness evolution 反复评估候选 harness、消耗大量 feedback 与 inference 预算，如果 baseline 只做一次朴素 test-time scaling，两者比的根本不是"harness 好不好"，而是"你花了几倍算力"；(2) 搜索集 = 评估集——unit tests 搜索出来的 harness 直接在同一个 benchmark 报告最终分数，构成了 harness-level 的 train-test 泄漏——好比在训练集上过拟合的模型来标榜"泛化能力"。

方法：匹配预算 + Held-out 双拷问。作者的实验协议追求严格公平：(1) 匹配 feedback 与 inference 预算——把 harness evolution 的所有搜索 tokens 折算成 baseline 的 test-time scaling budget（如 best-of-N sampling / self-consistency / 简单 ReAct 重试）；(2) 引入 discovery baseline——用同样预算做任务级简单搜索 而不做 harness 层面搜索，测试"harness 层" 是否真的比"任务层" 增益更大；(3) held-out 泛化——把演化出来的 harness 冻结、丢到未曾用于搜索的任务集 上重新评估，看是否仍保持增益。实验平台：Terminal-Bench 2.1（agent 系统级评估首选）× GPT-5.4 与 Claude Opus 4.6（2026 H2 顶级基础模型）——阵仗刻意做到"你没法说是因为模型太弱"。

结论与突破：(1) automatic harness evolution 不能 consistently 击败简单 test-time scaling——很多"harness 演化的增益" 在同预算下会被 best-of-N 打成平手甚至更低；(2) 演化出的 harness 泛化性有限——在 held-out 任务上收益显著下降，坐实"benchmark 过拟合" 猜测。H2 harness 谱系第一次"反思派" 登场——第十二层：Evaluation Protocol Critique 层（评估协议批判层）——与 7-14 的 Meta-Optimization 层构成"矛盾对立" 平衡关系：一个人在造更聪明的 harness 自动化，另一群人（UW + AI2）在拷问"这些自动化到底是真进步还是评估幻觉"。哲学突破：harness engineering 不能只关心"我造得多快"，还必须关心"我在哪把尺子上量的"——从建造派 (Constructive) 走向 批判派 (Critical) 的自我审视是任何工程学科成熟的必经之路，本文是 harness engineering 走向成熟的方法论里程碑。

评估协议feedback 预算inference 预算搜索/评估分离结论可信度

控制 inference 预算不控制匹配无中 —— 排除单次 inference 差异，但仍混合搜索红利
本文：匹配 feedback + inference 预算 + held-out匹配匹配held-out 任务分离高 —— 唯一能真正判定"harness 设计" 是否胜出

逻辑陷阱：如果不匹配 feedback 预算，那么 evolution 消耗 100 次单元测试的反馈，而 baseline 只做一次朴素推理——所谓"evolution 更强" 本质是"多花了 100 倍算力更强"。这个批判与 7-08 我们报告的 Harness MDP RL 训练也有部分共振：方法论上必须给"训练/搜索成本" 一个显性 budget line。

对研究方向的启发
对 Harness Engineering

H2 harness 谱系再拓展一格 · 第十二层：Evaluation Protocol Critique 层（评估协议批判层）——七层图 + 经济学层（Writer AI）+ Test-Time 演化层（TTHE）+ OS 执行层（ActPlane）+ Meta-Optimization 层（Yang/Kästner）+ 本文 批判反思层。这一层与第十一层 Meta-Optimization 层构成"矛盾对立" 平衡关系：Meta-Optimization 在造更聪明的 harness 自动化，Critique 层在拷问"这些自动化是不是真的赢过 test-time scaling"。方法学可复用：(1) 匹配 feedback + inference 双预算——任何 harness 自动化论文都应报告 baseline 的等预算表现；(2) held-out 任务——搜索集与评估集必须分离，否则涉及 harness 过拟合；(3) discovery baseline——加入"任务级简单搜索" 作为对照，测试"harness 层" 是否真的比"任务层" 更值得投入；(4) 结论粒度——不再讨论"演化好不好"，而是"演化在多少任务集上、多少预算下、多少泛化范围上真正胜出"。下一步预测：Meta-Optimization × Critique 双方阵抗衡 将快速催生新一批高质量 harness 自动化论文——因为方法论门槛已经被抬高。

对 Agent Safety

本文的"匹配预算 + held-out 泛化" 方法论对 agent safety 有直接迁移价值：(1) safety benchmark 演化也可能过拟合——如果一个 safety training method 在自建 benchmark 上迭代改进，那"泛化到未见 attack" 才是真实力，而不是"在训练 benchmark 上跑高分"；(2) 匹配 feedback 预算——今天我们已知 red-teaming 是 iterative process，如果 defense method 消耗 100 轮红队反馈，baseline 只用 1 轮，那 defense 的胜出是红队预算的红利；(3) 与 今日 agent-safety 报告 SLBench (Chen, Wang, Yan, Zhang @ Purdue) 呼应——SLBench 报告 70% unsafe rate 是一个诊断信号，但如果任何 defense method 在同 benchmark 上迭代改进，我们也应担忧 "safety-benchmark 层过拟合"；(4) safety evaluation 亟需自己的 held-out 协议——本文提供了 harness engineering 版本，safety community 应该复制这一方法论。

对 Benchmark

Agent benchmark 设计原则的又一根本性升级——benchmark 不再是"给定固定 evaluation set，看谁最高"，而是必须显式承担"held-out 泛化" 的责任：(1) benchmark 应内置 train / dev / test 三分划——像传统 ML benchmark 一样，让 harness 自动化 / RLHF / red-teaming 方法在 train 上迭代、在 test 上报告；(2) 匹配预算表格——benchmark 应要求所有提交报告"总 feedback tokens"、"总 inference tokens"、"总 candidate 数"，让不同方法在等预算下可比；(3) 与 今日 benchmark 报告 "How Many Tasks Are Enough" (Huang, KDD 2026) 呼应——Huang 的工作证明部分预算就足以支持大部分 benchmark 结论（AppWorld 15% / tau-bench 25% / SWE-bench 90%）——如果 benchmark 只需要 15% 就能拉出决策，那我们就能把剩余 85% 变成"held-out 泛化" 池；(4) H2 benchmark 方法学第十三联：Held-Out + Budget-Matched 联——从"锁定评估集比方法" 抬到"分离评估集 + 预算平权 比方法"。
