2. 一句话核心贡献
让 harness 从"部署时冻结的静态脚手架"变成"从自己执行经验里学习的自适应控制器"——test-time 无 label 无 feedback 即可为每个 case 检索并适配。
3. 摘要中文翻译（忠实原文）

Agent harness 是把 base LLM 变成可执行 agent 的外部控制层——它管理 context / tools / orchestration / memory / decoding / output handling。Harness 设计对 agent 行为影响巨大，然而当前的自动改进方法多聚焦更窄的对象（prompts / pipelines / workflows），部署 agent 通常也是所有 case 复用单一全局 harness。

本文提出 MemoHarness——一个自适应 harness 优化框架，从自身执行经验中学习。MemoHarness 把 harness 分解为六个可编辑的控制维度，把 per-case 诊断和 distilled 全局模式存入双层经验银行 (dual-layer experience bank)，并用检索到的经验对每个测试 case 适配学到的 harness，无需 test-time labels / feedback / 额外搜索。

在 shell-agent / code-generation / analytical-reasoning 三大 benchmark 上，MemoHarness 显著优于所比较的固定 harness，并展现对未见 suite 和 base model 的选择性迁移；当大量检索到的经验可缓存时，额外 context 依然能保持成本竞争力。这些证据支持：execution experience 是构建"比单一静态配置更自适应" harness 的实用底座；更广的统计鲁棒性与组件归因主张留待未来工作。

4. 核心内容解读（背景 · 方法 · 突破点）

要解决的问题（背景与动机）。 2026 上半年 harness 谱系集齐 13 层（context / 策略 / 循环 / 评委 / 配置 / 统计 / 学习 / 经济学 / 测试时演化 / OS 执行 / 元优化 / 评估协议批判 / 可靠性理论）——但几乎所有方法都仍产出"单一全局 harness" 供所有 test case 复用。这就带来两个显性缺口：(1) 单个 harness 无法覆盖 case 分布的宽度；(2) harness 一旦冻结，就无法把已经执行过的 case 里蓄积的诊断信号回灌到新 case。7-14 CMU Better Harnesses 组从"任务难度可迁移到 harness" 侧提出 meta-agent；7-15 UW+AI2 组则从"评估协议批判" 侧质疑"更好 harness 增益 vs 搜索红利"。MemoHarness 是从"经验重用" 侧提出的第三条路径——不追求 offline 训练更好的 meta-agent，也不追求评估协议纠偏，而是让 harness 在 部署过程中就地自我更新。

核心方法（三件套）。 (a) 六大可编辑控制维度：context / tools / orchestration / memory / decoding / output handling——覆盖 harness 的全部执行栈；(b) 双层经验银行 (dual-layer experience bank)：Per-case 诊断层存储具体 case 的失败/成功模式；Distilled 全局模式层把跨 case 反复出现的规律凝练成可复用的 harness patch；(c) Test-time 适配：无 label · 无 feedback · 无额外搜索——只用检索到的经验对每个 case 动态调整 harness。这三件套的关键设计 是把"harness 增益" 与"case 特化" 解耦：全局层保证跨 case 迁移，per-case 层保证针对性。

与现有工作的关键区别。 与 7-14 CMU Better Harnesses 相比：Better Harnesses 是 offline meta-agent 生成静态适配，MemoHarness 是 online 从执行经验里 test-time 自我更新；与 6-30 CUGA FLO / 7-02 Loop Engineering 相比：Loop Engineering 是显式 loop 规格，MemoHarness 是 隐式 experience-driven 更新；与 7-13 ActPlane（OS 执行层）相比：ActPlane 下推到内核层执行策略，MemoHarness 上推到经验层适配 harness——两者在完整 harness 栈上顶底两端形成镜像。这就催生了 H2 harness 第十四层：Experience-Driven Adaptive 层（经验驱动自适应层）——与 7-15 Rethinking Evolution 层构成 "批判评估 → 建设方案" 的自然衔接：如果传统 harness evolution 存在"搜索=评估" 过拟合，那 MemoHarness 就是直接在部署过程里在线学习 的替代路径。

7. 对三个研究方向的启发
对 Harness Engineering 方向

H2 harness 第十四层：Experience-Driven Adaptive 层（经验驱动自适应层）诞生——与 7-15 Rethinking Evaluation Protocol 层"批判评估 → 建设方案"衔接，与 7-13 ActPlane（OS 执行层）"顶底镜像"合流。六大控制维度是 Harness Handbook（7-14）视角的可执行落地；双层经验银行 是把"case 特化"与"跨 case 迁移"解耦的经典架构。今后 harness 工程应关注：(1) 经验银行的容量与检索算法（RAG 视角）· (2) 六维度间的依赖 / 冲突 · (3) 与 KV-cache 复用的经济学耦合——正好与你毕设 SGLang 方向直接叠加：MemoHarness × SGLang prefix cache scheduler 是天然融合点。

对 Agent Safety 方向

Experience-Driven harness 打开"从失败中学 harness-level 安全" 新维度——传统 agent safety 更多是"外部输入侧防御"，而 MemoHarness 表明：过去执行的失败轨迹本身就是 harness 层的诊断信号。它与 6-21 AgentLens（hidden-state 层可解释）+ 7-08 Doomed（残差流 probe）+ 7-13 Boiling the Frog（多轮 artifact-state）合流——都是把 safety 从"输入-输出快照" 推向"执行状态或经验"。H2 safety 潜在派生：把 dual-layer experience bank 里存储"安全违规模式" 而非仅"性能诊断"，就是"safety-aware MemoHarness"——per-case 遇到红线立即从全局经验层加载防御 patch。

对 Safety Benchmark 方向

Experience-Driven harness 让 benchmark 面临新一层"评估公平性" 挑战：如果 harness 在部署时可以持续从经验里适配，那"benchmark 分数" 是初始快照 还是经验充分后的稳态？（这与 7-15 Huang partial-evaluation 有类似哲学）。作者选择性迁移 的诚实报告正好呼应 7-14 Solozobov Load-Bearing Evidence——benchmark 需要为"experience-driven harness" 定义新的报告协议：报告 "cold-start / warm-start / cache-hit rate / experience-age" 四条曲线，而不是单一 pass@k。这就自然引出 H2 benchmark 潜在新联：Experience-Aware Benchmark 联。
