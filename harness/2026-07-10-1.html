一句话核心贡献
首次把 可执行 harness 变为 test-time adaptation 的状态本身 —— 用未标注执行轨迹在评估期间演化 harness，无需模型权重更新或标注监督。
摘要翻译（忠实原文）

一个 LLM agent 的行为不仅由底层模型决定，还由其 harness 决定 —— 即那个构造 context、调用工具、验证中间结果、从失败中恢复的可执行程序。现有做法在部署之前 优化这样的 harness：在训练或开发数据中搜索一个固定的 agent workflow，然后在测试时冻结它。这限制了适应能力—— 当测试分布、失败模式、工具交互与开发时不一致时。我们提问：harness 能否在评估本身期间被优化，仅使用 agent 在测试输入上产生的未标注执行轨迹？ 我们引入 Test-Time Harness Evolution (TTHE)，它把可执行 harness 视为 test-time adaptation 的 state。评估过程中，TTHE 维护一个候选 harness 群体，通过一个 agentic proposer 基于执行轨迹推理来精化它们，无 gold labels，无任务特化监督；judge 则从执行派生的代理信号提交改进后的 harness，被选中的程序持久化以治理后续输入。关键地，TTHE 不更新模型权重、不需要 gold labels、不训练一个独立的适应模型：solver、proposer、judge 都是围绕同一冻结 LLM 的不同角色与 harness，因此所有适应都通过对周围程序的改动发生。在 text-to-SQL、竞技编程、软件工程、数据科学编码、agentic 工具使用 5 大任务族上，TTHE 改进了固定 ReAct 式的基线 harness，产生持久、可检视 的改进，而非事先搜索好的 workflow 或按查询重试。这些结果将 LLM agent 的 test-time adaptation 重新定位为对可执行控制程序的演化，并识别出 执行派生的代理可靠性是稳健无监督 agent 改进的中心挑战。

核心内容解读（约 550 字）

解决了什么问题：进入 2026 H2，agent harness 的设计已从"临时脚手架"演化为影响 agent 行为的头等变量（参考 7-04 Belief Divergence · 7-08 Harness MDP · 7-09 Harness Effect 三篇独立证据）。然而所有既有工作都停留在 train-time / deploy-time optimization：预先在开发集上搜到 workflow，然后冻结整个 harness 部署。这在测试分布漂移、失败模式变迁、工具交互差异出现时会立刻退化。作者提出决定性反问：能否只用测试输入上的未标注执行轨迹，在评估过程本身中优化 harness？

核心方法：三角结构。TTHE 用三个"围绕同一冻结 LLM 的不同角色 harness"构成闭环 —— Solver harness：执行当前任务并输出未标注轨迹；Proposer harness：基于历史轨迹推理并提出改进的 harness 候选（新增反思、重排工具、改校验策略等）；Judge harness：从执行派生的代理信号（如 trace consistency、tool-return validity、self-report）判断新候选是否改进并 commit。整个过程不更新模型权重、不需要 gold labels、不训练独立适应模型——被 evolve 的只是周围的可执行程序。TTHE 维护一个 harness 群体，选中的程序持久化，治理后续输入。

关键实验结果：TTHE 在 5 大任务族上一致击败 fixed ReAct 基线：text-to-SQL（结构化数据库查询）· 竞技编程（LeetCode 式算法）· 软件工程（SWE-bench 式 repo-level patch）· 数据科学编码（Kaggle 式 pipeline）· agentic 工具使用（多轮 API 调用）。改进具有两大关键性质：持久性（不是 per-query retry 且会遗忘，是把学到的改动固化到 harness 程序里）和可检视性（新 harness 是可读的可执行程序，便于人类审计、迁移或再优化）。

与现有工作的突破点：三条独立立场。（i）区别于 7-08 Learning to Control Harness (Yi/Song 学习派)—— 那是离线 RL 训练一个 MLP 控制器，需要预先滚动数据 + 奖励信号；TTHE 是在线、无奖励、纯代理信号驱动，且演化的是可执行程序本身而非策略参数。（ii）区别于 test-time compute（每 query 多次采样）—— TTHE 的改进跨 query 累积到程序上，而不是每次重算。（iii）区别于 7-09 Harness Effect（Writer AI 手工优化 orchestration）—— TTHE 是自动发现那些手工优化才能触及的改动。H2 harness 谱系再拓展一格：第九层 · Test-Time 演化层——七层图（学习派收官）+ 第八层经济学层（Writer AI）+ 本文的 test-time 演化层。作者同时把execution-derived proxy reliability 提为无监督 agent 改进的核心开放问题：judge 用于打分的执行代理信号本身有多可信？这是把整套框架落地的信任瓶颈。

关键性质：持久性（改进固化到 harness 程序、跨 query 累积）× 可检视性（新 harness 是人类可读可审计的可执行程序）× 无监督（无 gold labels、无奖励信号、纯 execution-derived proxy）—— 是三者同时具备的首个方法。

TTHE 三角结构：围绕冻结 LLM 的角色 harness
角色 harness输入输出关键约束
Solver当前任务 + 当前 harness执行轨迹（unlabeled trace）使用当前候选群体最优 harness
Proposer（agentic）历史轨迹 + 当前 harness候选 harness 改动提案（可执行程序 diff）基于轨迹推理，不依赖 gold labels
Judge候选 harness + 执行代理信号commit / reject 决策依赖 execution-derived proxy（本文核心挑战）

三者共享同一冻结 LLM：solver/proposer/judge 只是 LLM 外部的不同角色 harness——所有适应都通过对周围程序的改动发生，而模型权重、gold labels、独立适应模型 三者一概不需要。这就是"harness as state"的严格形式。

对研究方向的启发
对 Harness Engineering

H2 harness 谱系再拓展一格 · 第九层：Test-Time 演化层——七层图（context/策略/循环/评委/配置/统计/学习派）+ 第八层经济学层（7-09 Harness Effect）+ 本文第九层 test-time 演化层。方法学可复用：(1) "harness as state" 抽象——把可执行程序视为 TTA 的 first-class 变量，脱离 policy/prompt 二元；(2) 三角结构 (solver/proposer/judge) 是可迁移到 lm-evaluation-harness / OpenAI evals 的即插即用架构；(3) execution-derived proxy reliability 应成为 harness 报告的新标准指标——这是无监督改进的信任基础。与 7-08 Yi/Song 学派形成"训练时 (Harness MDP) × 测试时 (TTHE)" 完整时间轴——H2 harness 学习派终于闭合。

对 Agent Safety

本文的 judge 依赖 execution-derived proxy signal 是安全侧最关键的漏洞：如果 judge 只看执行代理信号（trace consistency 等），那么规避 proxy 但语义不安全的 harness 改动可能被 commit —— 类似 reward hacking 但发生在 harness 演化层。启发：(1) TTHE proposer 需要引入 safety-aware constraints——例如 tool-payload governance、consent gate 等作为硬约束而不是软代理；(2) 与 今日 agent safety 报告 (Predicting LLM Safety Before Release by Simulating Deployment) 形成互补：Deployment Simulation 用历史部署 prefix 预测未来 misbehavior，TTHE 则可能在测试时演化出 未曾在部署 prefix 中出现的新 misbehavior 模式——两者共同构成"预测 × 演化" 双侧安全评估协议。

对 Benchmark

"benchmark 分数是 harness 依赖的" 得到新证据——TTHE 在测试期间演化 harness，说明同一模型 + 同一 benchmark + 不同 harness 演化程度 → 不同分数。leaderboard 必须显式标注：(a) 允许 test-time harness 演化吗？(b) 演化预算多大？(c) 是否隔离 judge 代理信号？。启发：(1) 引入 "TTHE-locked" vs "TTHE-allowed" 两个 leaderboard 变体——前者用固定 harness，后者允许 TTHE 演化；(2) 把 execution-derived proxy reliability 作为 benchmark 的元变量——benchmark 设计者必须提供"proxy 可信度"审计通道，否则 TTHE 类方法在此 benchmark 上的分数就不可比。H2 benchmark 方法学第十联：演化透明性联——benchmark 需暴露 harness 演化状态。
