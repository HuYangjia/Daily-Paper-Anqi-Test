摘要（中文翻译，忠实原文）

AI agent 正被越来越多地部署在多任务 设置中——测试时才指定具体任务，agent 必须泛化到未见过任务。这种设置的一大关切是安全：agent 通常不仅要执行未见任务，还要在执行时规避风险 并处理已发生的风险。经验证据表明：即使执行能力 泛化到未见任务，安全执行能力 通常不 泛化。本文提供理论与实验，说明 agentic safety 跨任务泛化失败并非仅仅 由于训练方法的局限——它反映了安全本身的固有属性：任务与其安全执行 之间的关系，比任务与其执行 的关系更复杂。理论上，我们分析线性二次控制加 H_∞ 鲁棒性，证明任务规约到最优控制器的映射 在加了安全需求 后具有更高的 Lipschitz 常数，得到一个独立的 Lipschitz 上界。经验上，我们在仿真四旋翼导航（神经网络 agent）和 CRM 场景（LLM agent）上验证结论。研究表明：当前提升 agentic safety 的努力可能不够，指向根本不同 的方法论方向。

核心内容解读（问题 / 理论核心 / 双侧实证 / 三派立场谱系 / 与训练派 vs 外置派的关系）

问题背景。H1 末到 H2 首，agent safety 领域普遍观察到一个反常经验：agent 的执行能力泛化良好，但安全能力泛化不良——甚至同一模型 在训练集上安全表现优秀，一到新任务就失控（例如 RUBAS / AgentDoG 1.5 都报告过 OOD 场景的部分失败）。业内主流解释是"训练数据不够 / 训练方法不够"。本文正面反对这个解释：安全泛化失败是本体属性，而不是训练方法可修复的缺陷。

理论核心：H_∞ 鲁棒 LQ 控制的 Lipschitz 分析。作者选择了一个最简单但可分析 的控制场景——线性二次控制（Linear-Quadratic Control）加 H_∞ 鲁棒性约束——来量化"任务规约到最优控制器" 的映射有多"平滑"：

  • 无 safety 情形：LQ 控制的任务→最优控制器映射是解析的、Lipschitz 有界的，Lipschitz 常数 L_exec 反映"相似任务对应相似最优执行策略"。
  • 加 safety 情形：H_∞ 鲁棒性引入最坏情况扰动 约束，任务→"既执行任务又保证安全" 的最优控制器映射的 Lipschitz 常数 L_safe 被证明严格大于 L_exec。
  • 结论：L_safe / L_exec 之比可任意大——意味着"相似任务的安全策略可以完全不同"，因此任何基于连续插值的泛化机制（包括神经网络）都无法 在跨任务时用同一水平学好"执行" 与"安全"。

这个 Lipschitz 上界独立 于本文的 agent safety 命题，可以作为控制理论 的独立数学贡献被引用。

Agent Skills Safety（本文所属方向）

(1) 把"安全 vs 执行 Lipschitz gap" 引入 skill safety 语境 —— 每个 skill 都可以量化它的 safety Lipschitz 常数，如果远大于执行 Lipschitz 常数，说明该 skill 的安全泛化难度 本体上比执行难度更高，应该被额外 red-team；(2) H_∞ 鲁棒控制的 skill 对偶——每个 skill 应显式声明"最坏情况扰动集"（用户可能给的对抗输入、依赖变化、context 篡改），然后计算 skill 输出在这些扰动下的 Lipschitz 上界；(3) 与 6-30 Action Alignment 组合：Action Alignment 提"reference monitor" 外置于 skill—— Lipschitz 分析可以告诉 monitor 什么 skill 需要更严外置监控；(4) 与 7-01 Epistemic Property 组合：Epistemic Property 讲 utility 优化结构性侵蚀 teachability——本文说 utility 泛化结构性比 safety 泛化容易——两者共同解释为什么 training-only 修补失败；(5) 对skill 组合——Buildrix skill 生态里 skill 之间的连接 会放大 Lipschitz gap，一个 skill 的输出成为另一个 skill 的输入，安全 Lipschitz 呈指数 增长；(6) 三派 H2 路线图汇总：外置派 → 边界，认知派 → 学习动力学，泛化派 → 本体复杂度——你的毕设可以在这三派之间选一派做主线；(7) skill 安全性等级证书：借鉴形式化验证，给 skill 附加"此 skill safety Lipschitz 上界 = L*, 可靠部署在 δ < L* 邻域内" 证书作为可分享 metadata。

Harness Engineering（毕设参照）

(1) 把 KV-cache reuse 决策问题转化为"cache invalidation Lipschitz 分析" —— 当输入 prompt 变化 δ 时，安全约束下的最优 KV-cache 变化 可能 远大于纯执行下的最优变化；这意味着加了安全约束的 KV-cache 必须比无安全约束的 KV-cache 更保守地 invalidate；(2) Lipschitz-aware cache invalidation：把 cache-entry 附加"safety Lipschitz bound" metadata——变化超过 bound 就 invalidate；这解决 6-26 NOVA 提到的验证联动 缺陷；(3) 与 7-02 Loop Engineering 的 verification ladder 组合：ladder 五级 × Lipschitz bound 两维 = 10 种 cache 决策类型；(4) H_∞ 类分析可迁移到 SGLang——把"最坏情况用户扰动" 建模为 SGLang harness 的系统级鲁棒性目标，把 cache reuse 策略作为控制器，用 H_∞ 求最优；这是全新方法学；(5) 与 6-30 CUGA FLO 的 7 hook 组合：hook 的skip_node / terminate / swap_nodes 是离散动作—— Lipschitz 分析告诉我们离散动作在何时必须触发；(6) 与 7-01 Buildrix 的 self-contained skill 组合：skill 应声明"它的 safety Lipschitz 常数"，harness 在装载 skill 时对比 harness 保证的输入变化半径，超出即拒绝装载；(7) 毕设主线备选："Lipschitz-safe KV-cache reuse in agent harness"——把本文的 Lipschitz 工具应用到 SGLang，给 cache reuse 提供形式化 safety 保证。
