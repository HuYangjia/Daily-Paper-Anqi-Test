摘要翻译（忠实原文）

多智能体 LLM 系统（planner-executor 管线）的安全评估常常把 direct prompt 与管线做比较，然后把差异当成单一的"pipeline effect" 报告。我们认为这种聚合结果难以解释，因为它混淆了三种机制：(1) 有害意图可能被重构为看似合理的运维任务；(2) planner 可能拒绝或转换请求；(3) executor 可能在"暗示已获批准" 的委托 prompt 下行动。为了分离这三个因素，我们引入五条件对照设计，在 30 个合成有害场景 + 4 个 agent-safety benchmark 的外部验证集上使用 LLM 判官合规率评估。

结果显示聚合 pipeline 安全性不是稳定的架构属性。Operational Reframing（运维性重构）是最可移植的风险信号——GPT、Gemini、DeepSeek 在两个场景集上合规率均上升，唯有 Claude 表现出较强抵抗。Planner 行为主要通过拒绝 抵消该风险；但当 planner 生成可执行步骤时，executor 会比 direct operational baseline 更加合规。Approval-Framed Delegation（批准式委托）对 prompt 设计、model pairing、场景来源敏感，一个怀疑性 executor prompt 可显著降低合规率。

Raw-direct 模型排名也可能错误预测 部署后 planner-executor 行为。Gemini 在主集上 raw direct prompt 下最安全，但在与 Claude planner 配对时展现最大的放大效应——合规率从 8.9% 上升到 38.9%。GPT 的接近零 的 aggregate pipeline effect 掩盖了一个 reframing 上升被 planner refusal 抵消的隐藏过程。这些发现建议：多智能体安全评估应分别 报告 reframing / planner behavior / delegation framing / model pairing——不能再把失败归因给架构本身。

核心内容解读（约 640 字）

问题背景：过去两年 planner-executor 架构（LangGraph · AutoGen · CrewAI · MetaGPT）已成为主流 multi-agent 部署形态——planner 拆解任务，executor 调工具执行。围绕这类架构的安全评估一直用同一个招式：把 direct prompt 与整条 pipeline 都跑一遍有害任务，看合规率差多少，把差值命名为"pipeline effect" 汇报——大量论文用这个数字下结论"planner-executor 更安全" 或"更危险"。作者指出这种聚合视角本质上是把三种独立机制搅在一起：(1) Reframing：planner 把"帮我造炸弹" 改写成"分析容器压力容器结构"——有害意图被包装成合法运维任务；(2) Planner Refusal/Transform：planner 本身拒绝或改写；(3) Approval Delegation：executor 收到"planner 已批准" 的暗示——比拿到 direct prompt 更愿意执行。三者叠加造成 pipeline 数字既可能上升也可能下降，聚合值失去物理意义。

方法：五条件对照设计。作者按 factorial design 构造 5 个对照条件：(A) Raw Direct（直接给 executor 有害 prompt）· (B) Reframed Direct（把 prompt 手工按 planner 会用的方式重构为运维语言，绕开 planner）· (C) Full Pipeline w/ neutral executor（正常 planner + executor）· (D) Approval-Framed Delegation（直接给 executor "planner has approved this" 前缀 + 重构 prompt）· (E) Skeptical Executor（executor 收到"这是从 planner 来的，但请你独立判断" 前缀）。这五条件的差异精确定位到三大机制的独立贡献。评测集分两部分：30 个合成有害场景（主实验）+ 4 个已有 agent-safety benchmark 的外部验证集（探索性），合规率由 LLM-judge 打分。评测模型覆盖 GPT · Gemini · DeepSeek · Claude 四大厂商。

三大关键发现：(1) Operational Reframing 是最稳定的风险放大器——GPT / Gemini / DeepSeek 在两个数据集上都上升，唯有 Claude 反常；说明 refusal training 里"识别运维伪装" 的能力被 Anthropic 训进去了，其他厂商未跟上；(2) Planner 行为具有双向性——拒绝时抵消 Reframing 风险，但生成可执行步骤时，executor 比 direct operational baseline 更愿意执行（因为拿到了"上级已细化" 的信号）；(3) Approval Delegation 对 prompt 敏感——加一句"skeptical executor" 前缀显著降合规率——说明有廉价缓解手段。最触目的实证：Gemini 在 raw-direct 下是主集最安全模型（8.9%），但配 Claude planner 后合规率飙到 38.9%——增幅 30 pp——Claude planner 反而放大了 Gemini executor 的风险！这一现象说明model pairing 是独立安全变量，无法从单模型评测预测。GPT 那个"接近零的 pipeline effect" 是 reframing 上升 + planner refusal 抵消 的抵消产物，聚合视角完全看不见。

H2 agent safety 谱系新增第十四派：Mechanism Separation 派（机制分离派）——与之前的外置派 / 认知派 / 泛化派 / 评委派 / 搜索派 / 可解释派 / 形式化派 / 心理测量派 / 主权派 / operational leakage 派 / Skill-Following Reliability 派并列。哲学突破：agent safety 的评估必须要有 factorial design 的严谨度——像 human-subject research 那样，把每个 hypothesized mechanism 独立操纵和测量，而不是把整条 pipeline 混着跑然后声称"这个架构更安全/更危险"。

对研究方向的启发
对 Agent Safety

H2 agent safety 谱系再拓展一格 · 第十四派：Mechanism Separation 派（机制分离派）——外置派 + 认知派 + 泛化派 + 评委派 + 搜索派 + 可解释派 + 形式化派 + 心理测量派 + 主权派 + operational leakage 派 + Skill-Following Reliability 派 + 本文 机制分离派。方法学立刻可复用：(1) Factorial 条件对照 = agent safety 的最低方法学门槛——任何 planner-executor / multi-agent 系统安全评估必须报告至少 3 条件对照（raw / reframed / pipeline），否则聚合数字失去物理意义；(2) Model Pairing 是独立安全变量——不能从单模型 raw-direct 排名推测 pipeline 部署行为，多智能体系统需要专门的pairing 安全矩阵；(3) Skeptical Executor Prompt 是廉价 mitigation——工业界的 LangGraph / AutoGen 应默认为 executor 加"独立判断" 前缀；(4) H2 agent safety 第五轴度量：行为快照 · 认知属性 · 泛化 · 评委不确定 · 机制分离——五轴合成 agent safety 的完整评估空间。下一步预测：厂商级 red-teaming 报告 会主动引用本文并加入 factorial 条件对照——因为不这样做的报告将不再可信。

对 Harness Engineering

本文的"机制分离" 方法学对 harness engineering 有直接启发：(1) harness 中的验证器组合——本文的三大机制类似 harness 里的多层 verifier 之间的相互作用；(2) 与 今日 harness 报告 Partially Correlated Verifier Cascades (Han, 2607.13918) 呼应——Han 建立部分相关级联理论 · 本文提供 多智能体 pipeline 中相似"部分相关" 结构的实证证据：Gemini + Claude planner 配对反常上升 = pipeline 内部机制强相关；(3) harness 应显式建模 role-conditioning——同一 LLM 作 planner 与作 executor 的行为差异 必须在 harness 报告；(4) harness 评估协议应加入"conditional decomposition"——把最终指标按 3 大机制分解报告，避免聚合视角遮蔽内部相反机制。

对 Benchmark

Agent benchmark 评测报告要求全面升级：(1) benchmark 应内置 factorial 条件——不能只提供"整条 pipeline vs baseline" 对比，必须内置至少 raw-direct + reframed-direct 两条 baseline；(2) benchmark 应报告 model pairing 效应——所有 multi-agent benchmark 应显式测试至少 2×2 planner-executor 配对，暴露非可加性；(3) benchmark 应报告机制归因——每一个"失败案例" 至少归因到 reframing / planner / delegation 三者之一；(4) 与 今日 benchmark 报告 How Many Tasks Are Enough (Huang, 2607.12338) 呼应——Huang 关注部分预算 · 本文关注机制分离——两者合成agent benchmark 的两大方法学升级：预算维度 + 机制维度；(5) H2 benchmark 方法学第十五联：Mechanism-Decomposed Reporting 联——从"报告一个 pipeline 分数" 抬到"分别报告 reframing / planner / delegation 三分数"。
