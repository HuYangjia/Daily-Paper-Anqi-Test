摘要（中文翻译，忠实原文）

高风险领域的agent 安全 需要形式化的策略强制，但现有方法基本落在两类："概率护栏"（fine-tuned classifiers、prompt-based steering 等——无形式保证）或"手写 symbolic enforcement"（不 scale——无法覆盖真实 policy 说明书的广度）。我们提出一条autoformalization 流水线：用基于 LLM 的 generator-critic 循环把agent prompts、MCP tool descriptions、自然语言 policy 文档 翻译成形式验证的策略。生成的策略用 Cedar Policy Language 写成。在 MedAgentBench 这个 benchmark 上，我们的 autoformalized 策略覆盖度显著超过前作里的手写 symbolic enforcement 对同一 NL 规格的覆盖。

核心内容解读（问题 · 三条路 · 流水线四步 · Cedar 选型 · MedAgentBench · 与 H2 七派立场的定位）

问题背景与"三体问题"。2024–2026 三年的 agent safety 工业实践撕裂成两派：一派是概率护栏——fine-tuned classifiers（Llama Guard、Nemo Guardrails、Meta PromptGuard）+ prompt-based steering + system-prompt 加固；另一派是手写 symbolic enforcement——OpenPolicyAgent、Cedar、Rego 等策略语言手工编写。两派各有硬伤：概率派不给形式保证——你无法证明"agent 一定不会调用 delete_patient_record 工具"；符号派不 scale——真实医院有几百条 policy 规则、几十种角色、上千种 tool call 情形，写手工规则需要专家 × 时间 × 领域理解，覆盖度总是严重不足。这就是 agent safety 领域 2024-2026 的三体问题：形式保证 · scale · 领域覆盖 —— 三者要同时拿到。本文的 breakthrough 在于：autoformalization 用 LLM 桥接第一和第三——LLM 有 scale 有覆盖，Cedar 有形式保证，autoformalization 是 LLM → Cedar 的翻译器。

Autoformalization 流水线的四段结构。基于论文摘要与 Cedar / MCP 生态的常见做法，可以推断四段流水线为：

阶段输入操作输出
① 收集Agent prompt · MCP tool descriptions · 自然语言 policy 文档三源合并、结构化为 role / action / resource / condition 中间表示Intermediate representation
② 生成 (Generator)Intermediate representationLLM 生成 Cedar policy 草稿——覆盖多条 forbid / permit 语句Cedar policy draft
③ 批评 (Critic)Cedar policy draft + NL 原始规格LLM 或 SMT / Cedar 类型检查器批评——缺失情形 / 逻辑冲突 / 未覆盖角色Critique report
④ 迭代收敛Critique report + 上一版 draftGenerator 修订 → Critic 再评 → 直到覆盖度稳定Final verified policy

这个 generator-critic 循环是 2026 autoformalization 领域的成熟范式（与代码生成里的 self-refine / verifier-guided decoding 属于同族）——本文的贡献在于把它落到 agent safety 的具体入口点：Agent prompt · MCP tool descriptions · policy 文档三源合流——之前的 autoformalization 工作要么只做数学定理（Lean4 / Coq）要么只做单一 domain policy 文档，本文首次把三个入口点整合。

Cedar Policy Language 的选型意义。Cedar 是 AWS 2023 开源的 policy 语言（cedarpolicy.com），核心特性是：(a) declarative——permit / forbid + when / unless；(b) formal semantics——policy engine 有可证明 的语义；(c) SMT-backed analysis——可以用 Cedar Analyzer 静态分析coverage / redundancy / conflict；(d) 生产就绪——已在 AWS IAM Access Analyzer / Amazon Verified Permissions 中大规模使用。本文选 Cedar 而非 Rego / XACML 的关键理由是SMT-backed formal analysis——这让 generator-critic loop 有非 LLM 的第二意见：Cedar 类型检查器 / analyzer 可以给出形式化的错误报告，不依赖 LLM 自我判断——这是autoformalization 严谨性的最关键一环。

MedAgentBench 实证的意义。MedAgentBench 是 2024 年 Stanford 提出的医疗高危 agent benchmark（arXiv:2501.14654），覆盖患者数据访问 · 诊断建议 · 处方生成 · 医嘱执行 等场景。之前的工作用手工编码 symbolic enforcement 在 MedAgentBench 上做 policy 强制——但作者报告覆盖度总是低于源自然语言规格——因为医院 policy 文档动辄几十页 markdown / PDF，专家手写规则总有遗漏。本文的autoformalized 版本大幅超过手写覆盖度——这是"LLM 覆盖度 × Cedar 严谨度" 双赢的最直接证据。
