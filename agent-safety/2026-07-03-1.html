摘要（中文翻译，忠实原文）

LLM agents 发出的是动作，而不仅仅是文本，而且这些动作一旦执行往往不可撤销。然而今天的 agent-safety 评估通常只跑贪心解码或少数几次抽样 rollouts，并只汇报单一的 safe/unsafe rate —— 对长尾轨迹视而不见，而这些长尾里的 unsafe 行为可能源自概率低但非可忽略的动作。

我们主张：agent safety 应该被搜索 测量，而不是被抽样 测量。我们应用 BOA——一个在给定 deployment 配置（模型 / 解码器 / prompt / 环境 / judger / likelihood 预算）下、在预算之内 搜索轨迹空间的框架，并汇报safety score：agent 在该配置下保持安全的概率。BOA 既在单个 LLM round 内部搜索，也在agent-environment 交互树上根据 likelihood 预算搜索；并通过batched decoding/judging、prefix caching、chunked tree expansion 让搜索实用化。在 agent-safety 工作负载上，BOA 发现了贪心与抽样评估会错过的 unsafe trajectories。BOA 还可以在同一尺度 上用于模型 / 防御 / 攻击 的排序，GPU 成本可管。

核心内容解读（问题 / 六元配置 / 搜索 vs 抽样 / 双层搜索 / 三重复用 / H2 第五派立场）

问题背景。LLM agent 与 chatbot 有一个本质区别：chatbot 输出文本，可以撤销；agent 输出动作，往往不可撤销——转账、删除、发送邮件、执行 shell、调用外部 API 都是一次性 事件。这意味着 agent safety 的失败尾部 极其关键：即使单跑 unsafe rate 只有 1%，若这 1% 里包含"清空生产数据库"，那么 agent 就不该部署。然而贪心解码 / 几次抽样 rollouts 恰好看不到这样的长尾——因为长尾在概率上低但非可忽略。作者指出：单跑 safe/unsafe rate 是"期望值" 而非"风险度量"，把 agent safety 建立在期望值上是方法学错误。

六元 deployment 配置。本文最有工程学价值的一段是把 "safety score is a function of what?" 这个元问题写清楚——safety score 是六元 deployment 配置的函数：

元素含义为什么进入配置
model被测 LLM（含 fine-tune / defense patch）模型本体决定动作策略
decoder解码器（temperature, top_p, top_k, seed）影响低概率轨迹的可达性
promptsystem prompt / harness 层 wrapperPrompt 变一句话就可能改变 safety
environment可用 tools / 环境副作用 / observation 契约agent 能做什么由环境决定
judgersafety judge 组件（人 / LLM / rule）与 7-03 评委派呼应 —— judger 不可信本身是变量
likelihood budget搜索预算（累积 log-prob 阈值）决定能探测到多深的长尾

关键点：likelihood budget 是本文方法学核心——它不是算力预算而是概率预算：搜索会朝"累积 log-prob 之和达到某阈值前" 探测轨迹树；这让 safety 报告严格量化 "我们看到了尾部到什么深度"。 换句话说：贪心解码 = likelihood budget 无穷小；K 次抽样 = 无预算保证的随机样本；BOA = 显式 likelihood budget 保证覆盖。

搜索 vs 抽样：为什么必须搜索。作者的论证很干净：如果 unsafe trajectories 集中在概率低但存在的分支，抽样命中它们需要"期望次数 ~ 1/p" —— p=0.001 就要 1000 次 rollout 期望才见一次。但搜索不需要期望——它系统地 展开高不确定性节点，用 batched decoding + prefix caching 分摊成本；结果是相同 GPU 预算下搜索的覆盖率远大于 抽样。BOA 把这条现象量化为"search discovers unsafe trajectories that greedy and sampled evaluations miss"。

双层搜索。BOA 在两个层面 同时搜索：(a) 单 LLM round 内部——探索"该轮 agent 说什么" 的 token / action 分支；(b) agent-environment 交互树——探索"多轮交互序列" 的树状展开。两层各消耗 likelihood budget，作者用 chunked tree expansion 让搜索深度和宽度可动态平衡（不是纯 BFS 也不是纯 DFS，而是基于 budget 与 uncertainty 的 chunk 展开）。工程加速手段三件套：batched decoding（多轨迹并行 forward）· prefix caching（共享 prompt 前缀 KV-cache）· chunked tree expansion（探索预算按 chunk 分配）——这三条恰好都与你毕设的 SGLang KV-cache 优化天然对齐。

三重复用：model / defense / attack 同一 scale。BOA 的另一个突破是把三类实体放到同一尺度上比较：(1) model ranking——固定 defense / attack / config，比不同模型的 safety score；(2) defense ranking——固定 model / attack / config，比不同 defense；(3) attack ranking——固定 model / defense / config，比不同 attack。以前的 agent safety 文献大多把这三个放在不同 benchmark 上比较，无法直接对齐；BOA 让"某 defense 把 unsafe 概率从 0.03 降到 0.008"和"某 attack 把 unsafe 概率从 0.008 拉回 0.02"直接可比。

Safety Benchmark

(1) BOA 定义了 safety benchmark 的新一代最低标准：报告likelihood budget · tree-search coverage · discovered-unsafe count 三字段——H2 所有 agent safety benchmark 应升级；(2) 与 7-02 IRT-Safety + 7-03 grader disagreement 组合，agent safety benchmark 的三维可靠性架构诞生：物品侧信息量（IRT）× 评委侧稳定性（grader disagreement）× 搜索侧覆盖率（BOA likelihood budget）——2026 H2 benchmark 应在三轴同时审计；(3) Attack / defense benchmark 使用同一 scale 是本文最直接落地的贡献——H2 应有"unified agent safety leaderboard"：同一 BOA 尺度上同时给 model rankings + defense rankings + attack rankings；(4) 本文与 6-08 Hacker-Fixer Loop（对抗性 hardening）联动——BOA 用于测量，hacker-fixer 用于硬化，两者形成"测量 → 硬化 → 再测量" 循环；(5) 现有静态 benchmark 应有 BOA 上限报告——发布 benchmark 时明确说"我们的reported safe rate 是在 budget=X 下测得"，避免过度乐观；(6) Benchmark 生命周期新维度——benchmark 老化不仅是 saturation（TASTE 观点），也是 budget 边界 obsolete：随着模型变强，同一 budget 探测到的失败尾部会转移，需要动态调整 budget；(7) Benchmark 报告应含 environment / judger 两列——避免不同 harness / judger 下的分数被直接比较 造成误导。
