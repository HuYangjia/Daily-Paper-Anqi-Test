一句话核心贡献
Skill 内部的逻辑关系（preconditions / constraints / fallbacks）本身是独立于 tool safety 的可靠性挑战——70% 公开 skill 含关系，Codex / Claude Code 在 SLBench 上 unsafe rate 最高 70%。
摘要翻译（忠实原文）

Agent skills 通过可复用的 procedures、tools 和领域特定 workflows 扩展 LLM agent 的能力，但其安全性依赖于正确解析交互指令间的依赖关系。我们引入 SkillLogic——一个用于分析 skill 文件中逻辑关系 并由此构建可执行测试的框架。我们的 taxonomy 覆盖 8 种关系类型，包括：preconditions（决定合法动作的前置条件）、constraints（限制允许动作的执行方式）、fallbacks（指定失败后的恢复行为）等。使用 SkillLogic，我们扫描了超过 5000 个公开 skill，发现70% 至少包含一种逻辑关系。我们进一步构建了 SLBench——一个由 high-confidence、high-impact、locally testable 关系构成的 86 案例可执行 benchmark。在 Codex 与 Claude Code × 6 LLM backbones 上评估显示 unsafe rate 最高达 70%，违规导致隐私泄漏、不安全的配置变更、cleanup 不完整。人类审计将失败归因为两方面：agent capability gap（能力欠缺）+ low-salience skill text（skill 文本可辨识度不足）。我们进一步展示 SLGuard——一个轻量级 inference-time scaffold——在目标案例上减少了 63% 的违规。我们的结果确立：logical-relation following 是 skill-guided agent 的独立可靠性挑战。

核心内容解读（约 560 字）

问题背景：2026 H2 agent 生态最大的架构转折，是"skill 作为一等公民" 从概念走向大规模落地——从 Anthropic Skills 到 Codex 内置 skill、从各类 skill marketplace 到 workspace-scoped skill——一个 agent 的行为越来越由 skill 文件 而非纯 LLM 权重决定。既有 agent safety 研究把注意力放在两处：(1) tool-call safety（工具调用的授权/边界，如 ActPlane 的 OS 层策略执行）；(2) prompt injection（对抗输入的注入攻击）。但本文提出一个被忽略的第三个维度：skill 文件本身内部 的逻辑关系是否被 agent 正确遵循。举个例子：一个 "deploy to production" skill 可能有 precondition "先跑测试"、constraint "只能改 staging 分支"、fallback "失败要 rollback"——如果 agent 忽略任何一条，就构成 unsafe 行为，但这不是 tool 层能防的，也不是 prompt injection 造成的，而是 skill-following reliability 本身的问题。

方法：SkillLogic 框架 + SLBench + SLGuard 三件套。(1) SkillLogic taxonomy——8 种关系类型（preconditions、constraints、fallbacks、以及其他 5 种未在摘要展开的关系）；(2) 大规模 skill 生态审计——扫描 5000+ 公开 skill，发现 70% 至少包含一种逻辑关系（意味着大部分 skill 都有"内部逻辑约束"，但没人评估过 agent 是否遵守）；(3) SLBench——从 high-confidence + high-impact + locally testable 三条筛选标准中挑出 86 个可执行案例（保证每个 case 都能用代码验证成功与否，避免 LLM-as-Judge 的主观性）；(4) 双 agent × 六 backbone 大规模评估——Codex 与 Claude Code 双 agent × 6 个 LLM backbone 组合；(5) SLGuard——inference-time scaffold（不改模型权重、不改 skill 文件），显式提醒 agent 关注 skill 中的逻辑关系。

实验结果与突破：unsafe rate 最高 70%——这意味着不管你选 Codex 还是 Claude Code、不管挂哪个 backbone，都可能在 70% 的高风险案例上违反 skill 内部逻辑关系。三大 failure mode：privacy leaks（跳过 sensitive-data 处理约束）· unsafe configuration changes（跳过 precondition 直接改配置）· incomplete cleanup（跳过 fallback 导致残留状态）——这三类在企业部署中都是典型 P0 事故。人类审计的归因很关键：不只是模型能力问题——也和 skill text 本身的 low salience 有关（作者写 skill 时该说"MUST"、该加显式检查列表却没做）。SLGuard 减 63% 违规 是一个务实的短期防线，但更深意义在于确立 skill-following reliability 为独立子领域。

H2 agent safety 第十三派：Skill-Following Reliability 派（skill 内部逻辑关系遵循派）——与 7-14 AISI 双边"操作性泄漏派"、7-13 EU AI Act "立法接地派"、7-10 "预测/模拟派" 并列。这一派把 safety 从"外部输入/工具边界" 内推到"skill 文件内部结构"——是agent safety 从"围墙" 走向"字里行间" 的关键一步。

核心洞察：Prompt 层与 Tool 层的防护无法防内容层违规——因为 skill 中的 precondition "在真实上下文里没被触发" 或 constraint "被 agent 遗忘" 都属于 agent 遵循 skill 文本 层面的失败，而非 prompt 或 tool 层面的失败。三层需要联合防御。

对研究方向的启发
对 Agent Safety

H2 agent safety 谱系再拓展一格 · 第十三派：Skill-Following Reliability 派（skill 内部逻辑关系遵循派）——七派体系 + 第八派"预测/模拟派"（Williams/Korbak, 7-10）+ 第九派"立法接地派"（Bisconti EU, 7-13）+ 第十派"操作性泄漏派"（AISI 双边, 7-14）+ 本文 Skill-Following 派。方法学可复用：(1) SkillLogic 8 类关系 taxonomy——任何 skill-guided agent 系统都可以套用（preconditions / constraints / fallbacks / ...）；(2) 5000+ skill 生态审计——为整个 skill marketplace 提供了生态级基线数据；(3) 可执行 benchmark 优先——SLBench 坚持 "locally testable + high-impact + high-confidence"，避免 LLM-as-Judge 的主观性；(4) SLGuard 短期防线 + 三层安全模型——inference-time scaffold 是企业当下就能落地的补丁；(5) 双因归因（capability + skill text salience）——引导 skill 作者社区建立skill 写作规范（何时 MUST、何时必须列 checkpoint）。下一步预测：SkillLogic × ActPlane × Prompt Layer 联合防线 —— 决策层（本文）+ 系统层（ActPlane）+ 输入层（Boiling the Frog）三层联合防御成为 skill-guided agent 的标配 stack。

对 Harness Engineering

本文对 harness engineering 的直接启发：skill 文件本身可以成为 harness 的一部分——skill 中的 preconditions / constraints / fallbacks 就是 agent harness 中"合法动作空间" 的显式声明。(1) SLGuard 是一种 inference-time harness modification——它不改模型、不改 skill，只在推理时添加 "attention to logical relations" 的 prompt scaffold；(2) harness 应当把 skill 逻辑关系变成 first-class control-flow 结构——preconditions → gate action、constraints → filter action、fallbacks → auto-branch on failure；(3) 与 今日 harness 报告 "Rethinking Harness Evolution" (Wang/Hajishirzi/Tsvetkov, UW+AI2) 呼应——本文提供了 skill-safety benchmark 的严格 protocol（可执行 + 局部可测），未来 harness evolution 应把 SLBench 加入 held-out 集，测试 harness 演化是否提升 skill logical-relation following（而不是过拟合到 unit test）。

对 Benchmark

Agent benchmark 设计的新范式：从"任务成功率" 抬到"内部逻辑关系遵循率"：(1) 双轴评估——一个 case 有两个正交维度：能否完成任务（capability）× 是否遵守 skill 内部约束（safety）；(2) locally testable 原则——本文的 86 case benchmark 每个都可以用代码判定 pass/fail，避免 LLM-as-Judge 主观性——这是所有严肃 safety benchmark 应遵循的黄金标准；(3) 生态级基线——扫描 5000+ 公开 skill 得到 "70% 含关系" 这类宏观统计，为benchmark 建立了外部现实校准；(4) 与 今日 benchmark 报告 "How Many Tasks Are Enough" (Huang, KDD 2026) 呼应——如果 15-25% 的 task 就能拉出决策（Huang 的发现），那 SLBench 的 86 case 完全够用，且可以留出大量 held-out 案例做泛化拷问。H2 benchmark 方法学第十四联：Skill-Following Reliability 联——从"外部对抗鲁棒" 抬到"内部逻辑遵循"。
