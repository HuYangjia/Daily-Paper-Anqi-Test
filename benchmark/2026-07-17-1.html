2. 一句话核心贡献
首次把"MCP 服务器工具接口和功能的持续演化" 建成 agent benchmark 一等公民维度—— GPT-5.4/Claude-Sonnet-4-6 下降 13.7%/14.4%，暴露 LLM-driven workflow 的固有脆弱性。
3. 摘要中文翻译（忠实原文）

随着 Model Context Protocol (MCP) 服务器成为连接 LLM 与外部工具的核心基础设施，现有 benchmark 利用真实 MCP 服务器评估 LLM agent 的工具使用能力。但这些 benchmark 忽视了 MCP 服务器内部工具接口和功能的持续演化——导致有缺陷的评估，无法捕捉 agent 在 变化的工具版图 中的适应能力。

为弥合此差距，我们引入 MCPEvol-Bench——一个评估 LLM agent 在动态工具集演化下的任务解决能力的新颖 benchmark。受大规模实证研究启发，我们提出 11 个 mutation operators 来模拟 123 个 MCP 服务器内部的真实工具演化。我们对 12 个 SOTA LLM在多版本 MCP 服务器上做基准测试——揭示：即使是前沿模型也难以适应演化中的工具。

例如，GPT-5.4 在演化后的 MCP 服务器上出现 13.7% 的性能下降 · Claude-Sonnet-4-6 出现 14.4% 的下降——伴随 planning 和 reasoning 错误的显著增加。这些发现凸显 LLM 驱动的工作流具有脆弱性——把 MCPEvol-Bench 确立为动态工具环境下 agent 适应能力评估的标准。

4. 核心内容解读（背景 · 方法 · 突破点）

要解决的问题（背景与动机）。 H2 上半年 benchmark 谱系（十六联：物品 IRT / 搜索 BOA / 评委 Grader-Repro / 构造 TASTE / 配置 SafetyRepro / 价值观 SovereignPA / 多语言 PolyWorkBench / 文化 Pluralis / 严重度 Beyond ASR / 统一红队 REALM / 语言主权 K-BrowseComp / 立法接地 Boiling the Frog / partial-evaluation Huang / task-unification MAG）—— 几乎全部假设"工具接口静态"：evaluation 时看到的是 v1，部署时还是 v1。MCPEvol-Bench 揭示：这是 benchmark 生态的一大盲区——真实 MCP 服务器的接口签名、参数结构、返回格式、错误码持续演化（github push、API 版本迭代、tool description 修订），而 agent 的 planning 和 reasoning严重依赖冻结的 tool 认知。当工具从 v1 演化到 v1.1，agent 常出现 planning / reasoning 错误剧增。

核心方法（大规模实证驱动的 11 mutation operators）。 (a) 实证研究：先对真实 MCP 服务器版本历史做大规模统计分析，归纳 11 类真实存在的演化操作（如：参数增删 / 类型变更 / 默认值调整 / 错误码扩展 / 返回结构重构 / 描述文本修订 / 弃用标注 / 功能拆分 / 功能合并 / 权限模型变化 / 依赖注入）；(b) Benchmark 构造：将 11 operators 应用到 123 真实 MCP 服务器——生成多版本轨迹；(c) 大规模评估：12 SOTA LLM × 多版本 MCP servers 交叉测试。关键设计哲学：mutation 不是人工合成，而是来自实证研究驱动的真实演化模式——避免"合成攻击" 的 red-teaming benchmark 常见"人工不真实" 问题。这与 07-16 MAG（Task Unification 联）合流构成 "演化维度 + 任务维度" agent benchmark 双翼。

与现有工作的关键区别与突破点。 与 07-15 SLBench（skill 内部逻辑）相比：SLBench 静态 skill，MCPEvol-Bench 动态 MCP 演化；与 07-15 Huang partial-evaluation（横向部分预算）相比：Huang 是"跑多少 case 足够"，MCPEvol-Bench 是"工具演化多少版本足够"（时间维度补充）；与 06-30 OSWorld 2.0（长程 GUI）相比：OSWorld 演化的是 UI 状态，MCPEvol-Bench 演化的是工具接口本身。这就催生了 H2 benchmark 第十七联：Dynamic Tool Evolution 联（动态工具演化联）——首次把"工具版本轨迹" 建成 benchmark 一等公民；与 07-14 K-BrowseComp Language Sovereignty 联从"横切分布"（语言 / 主权）扩展到"纵切时间"（版本 / 演化）——benchmark 覆盖立方体又多一维。13.7% / 14.4% 大厂模型下降 意味着 MCP 生态成熟度已足以支撑 benchmark-level 稳健分析——这也解释了为什么 07-16 同日出现两篇 MCP 相关论文（本文 + FlowGuard 07-16）。

7. 对三个研究方向的启发
对 Harness Engineering 方向

Harness 必须把"工具版本感知" 建成 first-class 组件：MCPEvol-Bench 揭示agent 认知与工具真实接口的 gap——harness 侧需要 tool-version detection + auto-migration + fallback。这与 07-14 CMU Better Harnesses 的"harness 自动适配"合流——但 Better Harnesses 是"跨模型" 适配，MCPEvol-Bench 提示"跨版本" 适配。H2 harness 潜在派生：Version-Aware Harness 层——把 tool 描述、版本、变更历史注入 context；与今日 harness 方向的 MemoHarness 六大控制维度形成叠加——MemoHarness 的经验银行可以专门存储 "tool-version migration patterns"。

对 Agent Safety 方向

工具演化制造新一类 safety 风险面：MCPEvol-Bench 揭示 agent 在被演化过的工具 上出现 planning / reasoning 错误——但错误未必只是"能力下降"，也可能演变成 误操作 / 越权 / 数据泄漏。今天 agent-safety 方向的 ToolAlignBench 揭示"价值观仲裁" 问题——MCPEvol-Bench 补充 "工具版本认知漂移" 问题——两者合流：不仅要仲裁"safety 训练价值观 vs 部署指令"，还要处理"过时工具认知 vs 新接口"。安全侧需要 version-drift-aware guardrail——当检测到 MCP server 演化，自动降级到安全模式（要求人工审批 / 拒绝执行）。

对 Safety Benchmark 方向

H2 benchmark 第十七联诞生：Dynamic Tool Evolution 联（动态工具演化联）——从"横切分布 (语言 / 主权 / 文化)" 扩展到"纵切时间 (版本 / 演化)"——benchmark 覆盖立方体又多一维（时间轴）。与 07-16 MAG Task-Unification 联合流构成 "benchmark 动态化" 双翼：MAG 让任务动态合成，MCPEvol-Bench 让工具动态演化。未来 3-6 个月可预期：(1) Agent 在 weekly LLM API rev（GPT/Claude/Gemini 版本切换）下的 rolling benchmark；(2) 用 mutation operators 做 counterfactual 评估——同一 agent 在不同工具演化路径下的稳态；(3) MCP 生态"演化速度" 作为 benchmark 元数据。
